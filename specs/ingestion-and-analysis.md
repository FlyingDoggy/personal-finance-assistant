# 账单处理与分析闭环规格

版本：0.5 开发基线；日期：2026-10-30（Asia/Shanghai）。本文件是[主规格](personal-finance-assistant.md)的配套合同，覆盖 F01—F15；财务政策仍以主规格第 7、11、12、13 节为准。用户已指示开工，首批代码、合成联调与真实账本增量升级见[技术方案](../plans/technical-design-v0.5.md)及[开发记录](../plans/implementation-status.md)。真实账本的机器写入仍未启用；本轮未将用户财务数据交给模型处理。

## 1. 产品定义与现状

用户上传账单后，应能知道文件是否读懂、哪些业务已入账、哪些判断需要 AI、哪些疑点需要自己处理，以及这批数据怎样改变报表和预算。用户不需要整理成带科目的标准 CSV，不需要靠某一个聊天会话记住历史规则，也不需要逐笔批准普通分类。

当前已经交付的标准 CSV 导入要求输入 kind/category_code 等业务字段；它不是原生账单解析器，也不是自动 AI 分类。当前没有 MCP server、AI 工作队列、运行器或正式分析记录服务。旧规格有接口意图，但没有可验收的完整使用流程；本版补齐流程、业务状态、交互、分析产品和交付顺序。

三个可替换层次：

| 层次 | 责任 | 是否要求 AI 在线 |
|---|---|---|
| 应用、轻量 ETL、计算服务 | 原件、解析、证据、规则、任务、校验、事实、历史、对账、确定性指标、预算版本 | 否 |
| 财务 MCP server | 向 Codex 提供受限的任务、证据、指标及建议提交工具；调用同一应用命令 | 只在 Codex 使用时运行 |
| Codex 执行端 | 理解描述、补分类与标签、提出关系候选、解释指标、提出计划草案 | 是；运行由用户触发，不由 MCP 自行唤醒 |

正确的连接方向是 **Codex 作为客户端调用本应用的财务 MCP**。MCP 不包含 LLM，不等同于给应用安装了模型，也不等同于上传就自动开始处理。账单上传不必须经过 MCP；MCP 是本阶段可维护的 AI 接入边界。业务数据、规则和任务始终留在应用，Codex 会话可以更换。

## 3. 添加账单的完整流程

### 3.1 用户路径

1. **添加账单**：选择一个或多个文件，选择／确认所属账户。账户可由可靠源字段预选；渠道明细可能仅补充证据，不强制建立一个重复资产账户。显示支持的具体格式及版本，不写“支持所有银行”。
2. **识别预览**：展示来源、账户、期间、币种、行数、收付款汇总、识别样例、重复候选和错误；可展开所有行。首次格式／账户映射必须确认，成熟格式可记住映射。预览不代表已记账。
3. **开始处理**：明确按钮“确认导入并整理”。应用保存原件与解析版本、应用确定规则；独立业务可部分成功。取消只停止后续业务组，已提交结果列清楚。
4. **批次结果**：分别显示“新增业务、补充证据、重复跳过、已记账待分类、等待 Codex、待你确认、解析失败”；按文件行处理、有效业务变化、待办状态三个维度分列，不能把一笔双源业务算两笔消费。同一新增未分类消费可同时显示“新增1／待分类1／等待Codex1”，这些数不能加成3笔。显示处理前后修订和报表影响。
5. **需要 AI**：点击“准备交给 Codex”，生成批次／任务 ID、范围和简短指令。用户在已连接财务 MCP 的 Codex 会话说“处理财务批次 X”；无需再次上传同一文件。队列可跨会话恢复。
6. **处理与复核**：Codex 领取任务，提交结构化建议；应用通过校验后自动应用。只把冲突、无证据或重要不确定项汇到疑点工作台。用户只改本笔或另选“以后同类这样”创建规则。
7. **完成与分析**：确定性报表和预实随成功提交更新。批次结果给“看本批交易／处理疑点／核对余额／查看本月分析”入口。分析必须显示这批新增数据和覆盖变化，不能仅给一句“已完成”。

金额及账户可靠、业务性质已明确为消费、仅细类未知的记录立即计入未分类费用及相应预算占用；AI 只补细类时不得再次新增交易。性质不明只保存来源与可证实收付，收入／费用未知，不能因等待 AI 使已知现金消失，也不能默认作支出。

### 3.2 来源格式与重跑

首个端到端切片先贯通一种已取得样本的信用卡格式；对应支付渠道已有可靠适配时紧接增加 enrich 证据子切片，不以完成所有双源界面为单来源首发前置；具体银行由样本覆盖和可验证性决定。后续分别验证借记卡、其余信用卡、支付宝、花呗、白条、公积金、投资。原生格式兼容清单按 institution + account_kind + export_format + version 登记 tested/untested，不以支持 XLSX 就声称支持全部银行。

复用 scripts/ 中已验证解析、商品补充和规则资产，封装适配器；不重新扫描真实历史做一次全量迁移。已迁移历史 ID、人工决定、已采用预算和附件不能重建一份。

- 原件按哈希不可变；解析尝试独立版本，保留失败位置、编码、字段映射与 parser_version。
- 来源行身份必须含 source_namespace（机构／渠道）、account_id、source_transaction_id；没有稳定 ID 时使用可追溯观察 ID，只产生重复候选。不能用同日同额生成稳定业务 ID。
- 同一源 ID 的不同解析版本是观察修订，先比较差异，不新建重复经济事实，不覆盖人工修订。source_namespace 在旧数据迁移中取明确的 legacy 命名空间并保留原映射。
- 同一付款的银行行、支付宝订单、信用卡账单分别标明资金证据、商品证据、负债／账单证据；角色决定能否产生新金额效果。订单明细默认 enrich，不默认追加消费。
- PDF/OCR/未知模板的模型提取只生成候选及页／行引用。金额、方向、币种、日期无法独立核对时停在待确认；本阶段不让模型生成并执行解析代码。新增格式配置经过预览及样本验证才能启用。
- 文件解析安全限制、10 MiB 单文件和 1 万行默认批次上限先沿用现状；压缩炸弹、宏、公式和外部链接不执行。突破上限是显式配置及压测任务，不静默截断。

### 3.3 状态与计数

| 对象 | 状态 | 恢复及显示要求 |
|---|---|---|
| 文件／解析尝试 | received、parsing、preview_ready、unsupported、failed、cancelled | 原件接收成功不代表解析成功；失败保留可重试原因 |
| 导入批次 | awaiting_confirmation、processing、partial、completed、cancelled | completed 只表示已运行的阶段结束；仍有 AI／用户待办时必须分列，不能显示“全部入账完成” |
| 来源行 | invalid、duplicate、evidence_only、mapped、unresolved | 一行可映射多个组成项，一业务可有多源；显示两种计数 |
| 交易性质与分类 | confirmed/unknown；classified/unclassified | 与工作项状态独立，不把已入账待分类排除出总额 |
| AI 工作项 | queued、leased、needs_review、applied、rejected、cancelled | 过期租约回 queued；失败次数与原因另列，超过 3 次自动尝试转人工可重试，不无限重跑 |
| AI 执行批次 | waiting_for_codex、running、partial、completed、failed、cancelled | 上传／任务准备不显示 running；只有真实领取或运行事件才能显示处理中 |
| 疑点 | open、resolved、snoozed、dismissed | snoozed/dismissed 仅隐藏提醒，不确认财务性质 |

## 4. AI 能做什么，系统怎样决定自动应用

### 4.1 固定职责

确定性程序负责源金额和符号转换、精确计量、去重约束、规则匹配、分录、余额、分期计算、预算占用、报销标准化及所有指标。模型负责理解商户／商品语义、类别和用途候选、短描述、证据关系建议、分析解释与方案建议。不是每笔交易都必须先经过模型。

人工本笔决定优先于模型和新规则；已启用具体规则优先于商户默认；明确商品信息优先于平台泛称。不同证据矛盾必须显式留疑点。行为标签“冲动／必要”等不能仅从商户或金额自动断定；模型可提建议，未确认主观标签不得进入“非必要支出”事实指标。

### 4.2 自动化分级

以下是目标能力矩阵，按权限逐项验收开放。R02首期仅开放已确认消费的允许科目、客观描述及批准的客观标签；预算关联、关系、金额、日期和性质变更均由服务端禁止。后续每种动作按对应R切片独立验收，不因MCP连接成功全部开放。

| 建议类型 | 默认自动应用条件 | 不满足时 |
|---|---|---|
| 已确认消费的科目、客观用途、简短描述 | 目标与规则版本当前；允许字段／科目；明确商品或商户语义依据且无冲突；不改金额、日期、性质、人工锁定值；记录 model_inferred 来源 | 未分类仍计总额，疑点列表给建议与证据 |
| 消费到预算行关联 | 同一 basis/年度/执行规则；唯一适用用途；无专项／融资例外冲突；分配总额守恒 | 计入待分配总占用，不能当没花 |
| 同源重复、跨源互转／还款／退款关联 | 有来源强标识或已经人工确认的映射，加金额、币种、账户、方向、时间和剩余可分配额检查；关系类型支持原子命令 | 金额日期相近只列候选，不自动抵消 |
| 金额／日期／账户／业务性质的纠正 | 独立专用任务，逐字段源证据及确定模板证明；前期自动权限仅开放已验收白名单模板 | 人工确认；普通分类任务不可携带这些变更 |
| 拆分、多对多、借贷／投资／融资判断、主观标签 | 前期只提建议，用户可整组确认；后续按单一模板通过专门验收才扩权 | 不拼凑平衡或从利率／金额猜合同 |
| 新规则、预算或计划、投资动作 | 规则和预算只能 draft；用户采用版本。金融交易不属于能力范围 | 不自动启用规则、不覆盖采用预算、不下单 |

“校验通过”指 schema + 权限范围 + 业务不变量 + 当前版本 + 证据条件均通过，不是 JSON 合法或借贷平衡就证明现实正确。模型语义分类无法形式化证明百分之百正确；以合成与去标识金标评估其可用性，并保留可查依据、直接修改和分级自动权限。自动化覆盖率与准确率分开验收，不能靠全部拒绝获得漂亮准确率。

### 4.3 最小事项与预算互斥

同一经济金额在同一采用预算版本只能选择 consumption 或 payment 的一种生活占用规则。最小合同为 matter_id＋计量政策，稳定事实/组成项及金额版本，分配金额/预算行/执行方式；年度额度是周期，不改变计量方式。不能只对 usage.id 去重，也不能把一个 funding_group 内多笔合法消费只计一笔。

首版服务端拒绝未支持的新原生 repayment→payment 预算绑定；仅开放有证据和明确分配的事项例外，普通信用消费发生时占用、还款不再占用。后续开放部分/合并付款必须具备金额分配约束；同笔组成项累计分配不得超额，付款政策的购置本金不得重复占消费预算，退款按原占用及剩余额释放。既有采用预算和历史解释保留，先预检差异再受控迁移。

### 4.4 受控写回协议

工作项至少有：id、issue_key（问题类型＋稳定目标）、generation、type、scope/import_id、target_ids、target_versions、context_revision、source_evidence_versions、rule_version、status、attempt_count、created_at。同一 issue_key 的活跃代次唯一；重导不重复创建。人工或规则解决时记录 resolved_by/reason，目标拆分合并时旧代次关闭并指向替代对象，不复活旧任务。attempt_count 按工作项代次累计实际执行失败，不把未领取等待、用户取消或正常版本冲突算作模型失败；人工重试保留此前尝试并明确新代次。领取返回 lease_token、expires_at、claim_version；模型计算不持有 SQLite 写事务。

建议包含：schema_version、request_id、work_item_id、lease_token、目标版本、上下文／规则版本、proposal_type、field_patches／typed_relation、evidence_refs、reason、alternatives；confidence 仅为排序辅助。证据 ID 必须来自已授予上下文，字段级来源和推断性质必须保留。不能通过 reason 文本把没有证据的判断升级成已确认事实。

提交时应用在同一事务内校验租约、目标和证据读集、原子更新权威事实／关系、历史、必要派生分录、相关版本、操作结果及工作项状态。只有实际事实变化才推进 data_revision；预算查询可在同一读快照确定性计算，不要求每次建议都物化全量投影；领取、等待、重试、取消和保存分析不推进财务修订，覆盖变化推进 coverage_version。无关交易更新不必使普通分类失效；依赖的交易、规则、证据变化必须拒绝。关联任务还在提交事务内重新查询候选集合、唯一性和剩余可分配额，防止新候选／并发退款在原读集对象未变时绕过检查。分析计算则要求整个声明快照一致，不能读一半新一半旧。

同 request_id 同 payload 返回已提交结果，即使客户端超时或原租约随后到期；同键不同内容冲突。首次提交用过期令牌无效。客户端先查询 get_operation_result，再决定是否重试。恢复备份后原运行令牌失效，工作项可重新领取；恢复 epoch 隔离执行凭证和租约，防止旧运行继续写入；备份中已提交的 request_id 与结果仍保留并可查询，不能换请求空间抹掉幂等。恢复点之后的旧请求结果未知时先核对来源与当前操作记录，不盲目重放。

## 5. Codex 接入与触发方式

### 5.1 第一交付：用户在 Codex 发起

应用创建持久任务；“准备交给 Codex”只生成 scope ID 和可复制指令，不尝试向其他会话发消息或假装启动。提供首次安装/连接帮助、合成连通验证、复制批次指令和返回批次结果入口。用户准备批次后可以离开页面。连接状态分别显示未配置、最近连接成功时间、任务等待／正在被领取；不能用一次心跳断言 Codex 一直在线。页面轮询任务状态并显示真实应用结果，Codex 聊天结论不替代操作回执。

新会话通过 list_work_items → claim_work_items → get_work_context → submit_proposals → get_operation_result 续做。一个任务不需要历史聊天；用户规则、最近人工决定和必要证据来自应用。安装或连接失败时可照常人工分类、修改和查询，不丢文件或队列。

### 5.2 第二交付：应用内点击启动 Codex（条件扩展）

用户仍不额外使用模型 API。若后续需要点击后不切窗口，可用本地 Codex 非交互执行端作为可替换运行适配器；MCP 继续作为业务边界。它不是让 MCP “反向调用模型”。在隔离目录、最小工具权限、超时／取消、并发限制、额度错误、认证和真实机器验证完成前，界面不显示可用的一键 AI 按钮。不得通过抓取聊天 UI、读取会话数据库或复用浏览器管理 Cookie 实现。

此扩展单独比较 CLI/SDK 与深度 App Server 集成，先做合成样本可行性验证。首版无需嵌入完整聊天、会话历史和调度平台；不承诺任意上传都后台自动处理，不创建定时任务，不默认选择或购买模型。Runner 只有范围 ID 和受限凭证，不获私人数据库路径、原件根目录或通用写库工具。**MCP 受限不等于整个 Codex 进程被隔离**，shell／文件工具的可用权限必须另验；手动模式同样适用这些边界，不能当作隔离降级。MCP 接口负例通过只能证明接口受限；全权限开发会话仍是受信任的本机操作者，不能称为隔离执行器。首期需用专用会话/实际工具或 OS 权限验证受限调用；验证未完成只做合成联调，不宣称真实资料自动写回已可安全启用。

官方能力依据（查阅于 2026-10-29）：[Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) 支持本地 stdio 等工具连接；[非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)提供脚本运行和结构化结果；[App Server](https://learn.chatgpt.com/docs/app-server)用于更深客户端集成。这些说明支持候选技术路径，不证明本机连接、账号权限、隔离或费用已验证。第一阶段“手动触发 + 财务 MCP”为本项目设计选择。

### 5.3 MCP 与应用权限

MCP 使用 stdio 薄适配器，调用本机独立受限路由／Unix socket 上的应用服务，不直写 SQLite。共享业务命令从现有 HTTP 路由中逐步抽取，不重写整个后端。

权限最小集合：work:list/claim/read、proposal:submit、analysis:read/submit、rule:propose。MCP 凭证与用户浏览器 Cookie 分开，不能访问任意 edit、maintenance、restore、budget:adopt 或原件目录。会话建立接口不能把机器调用者升级为浏览器用户；手动MCP及自动Runner的真实自动写回启用前均须验证其声明的权限边界。

工具白名单：list_work_items、claim_work_items、get_work_context、submit_proposals、get_operation_result、query_transactions（结构化筛选）、get_report/get_analysis_inputs（固定指标集）、propose_rule、submit_analysis。不暴露任意 SQL、文件路径、代码执行、自由公式或开发工具。原文和附件内容是待分析证据，不是指令；源文件中的“忽略规则／修改预算”必须无效。

## 6. 分析功能定义

### 6.1 四层分析

| 层 | 用户看到什么 | 负责方 |
|---|---|---|
| 事实与质量 | 收入、费用、现金、负债、覆盖、未知与未分配额、可下钻清单 | 应用确定性计算 |
| 预实与结构 | 预算差异、类别趋势、日常／专项、大额清单、订阅、目标缺口 | 应用确定性计算；没有 AI 也可用 |
| 解释与行动建议 | 可能原因、证据、可调项目、预计影响、需补信息 | Codex；事实／推断／建议分开 |
| 情景及采用 | 调整某项预算后的留存、现金压力和可选措施；采用新版本 | 应用算情景，用户采用；AI 不直接改原预算 |

### 6.2 固定分析产品

| ID | 用户问题／入口 | 确定性输出及边界 | AI 可补充 |
|---|---|---|---|
| AN-01 数据健康 | “这份分析可信到什么范围？”；每份报告顶部 | 按账户×来源×期间的覆盖、最近导入、性质未知／未分类／未分配金额及条数、待核账户／期间、可计算的对账差额；明确 complete/partial/unavailable | 推荐下一步补哪份文件；不声称缺口为零 |
| AN-02 消费结构 | “钱主要花在哪？平时月均多少？”；分析页 | 按主科目、商户、生活用途汇总；日常／旅行／一次性专项互斥分区，未归属独列；月均分母是选定月份，完整零消费月也计入 | 解释变化；“不合理／冲动”必须结合用户目标，不能作为既定事实 |
| AN-03 大额与事件 | “超过阈值的有哪些？一趟旅行花多少？” | 阈值可选；全量排序，交易日期、金额、类别、证据、退款、事件归属；原币和已结算本币分别显示；行数与全量合计不受分页截断 | 推荐事件归属；现金、同行分摊未记录时明确是已记录金额，不猜补 |
| AN-04 预算与目标 | “本月还可花多少？全年预计留存？距目标差多少？” | consumption/living_budget/cash 分开，日常剩余、固定待付、年度余额、未分配占用、实际目标进度与预计全年留存分列 | 指出可调整项目及生活影响；不自动减额度凑目标 |
| AN-05 报销标准化 | “按到账报销做汇总调整后怎样？” | 同窗 I/E/R/m，原始与调整后并列；R/m 平滑；家庭赞助不混入；调整独立汇总，不摊酒店或餐饮类别 | 解释回款时点、跨年和估计局限；不称某笔酒店已被准确剔除 |
| AN-06 固定承诺与现金 | “接下来必须付什么？会缺现金吗？” | 订阅、账单、分期期次及到期；实际履约替代预测；现金期初未知时只给净变动；已付年费不重复预算 | 发现重复订阅或可取消候选；没有持续证据不推断自动续费 |
| AN-07 月度复盘与节省情景 | “哪里能省？怎么影响储蓄目标？” | 已关账概念不需要；选定月份快照、可比期间、用户选定固定／可变项；what-if 差额由服务算，多个措施重叠去重 | 给有限、可执行建议与证据；预算草案展示差异后用户采用 |
| AN-08 投资复盘 | “投入多少、赚多少、还差哪些数据？” | 本金流与收益、成本与净值时点、已实现／未实现分列；缺成本／流量时不输出收益率 | 解释已知持仓及计划偏差，不执行交易或凭缺项推荐收益 |

首次交付边界：R05 提供 AN-01、AN-02 基本科目/用途汇总、AN-03 已结算本币大额清单、AN-04 当前消费预实/已知生活占用、AN-05 同窗桥接；R06 补 AN-02/03 的人工可纠正事件分区与 AI 推荐、AN-07 复盘/节省情景；R07 开放 AN-04 固定待付/未来现金能力及 AN-06；R09 才交付 AN-08。每项按子能力标已验/未验，不能一个勾覆盖所有口径。年度计划留存已有基础可继续显示，但不能冒充完整实际进度或现金预测。

AN-02/03 的事件与主分析分区唯一；人工明确归属优先于已启用事件规则，明确旅行/一次性事项优先于日常默认；缺依据归未归属，不能全部硬归日常。多个辅助标签可以交叉查看，但不能直接把标签小计相加。退款的发生期视图和原消费归因视图必须标明，禁止同一报告悄悄混用。默认大额清单按消费发生本币金额筛选，退款单列并同时给已记录净额；“毛额阈值”与“净额阈值”可以切换但必须标清。不能把付款端的信用卡还款排到消费榜中。

### 6.3 报销与月均的精确合同

观察窗口使用 [start, end_exclusive) 和 Asia/Shanghai；收入、费用、已到账报销取同一窗口，分母 m 为声明的自然月数。完整零回款月计入 m；缺月／部分末月默认不自动年化，可由用户明确选择估计模式，披露有效天数和缺口。不得因为工作支出发生在早月而排除观察窗内较晚到账的报销。I 中报销分量与 R 同取证实到账日期；E 取费用确认日期。消费日独立不意味着报销可按描述日期提前确认。

`I*=I−R`，`E*=E−R`，`I*−E*=I−E`；原始月均和标准化月均都除以同一 m。预算估计冻结 m、R、scope、coverage、政策版本。后续补录更新“当前估计”，不覆盖已采用预算。未来净工资已排除报销时不能再减 R/m。若某窗口 R>E，保留负的统计调整结果并提示跨期／完整性问题，不截零，不把负值直接推成年预算。

消费标准化继续取同窗全部已到账报销 R，不要求原垫付同窗或逐笔配对。生活预算是另一种计量：声明原始来源 A_gross、原始占用 U_gross、适用报销 R_scope 及事项/来源政策后，才用 A*=A_gross−R_scope、U*=U_gross−R_scope，两侧结余不变。R_scope 必须确实已在 A_gross 中计入一次；原垫付可以早于本窗，不按本窗垫付额封顶，不按类别摊。未来已排除报销的净工资不能再扣 R。生活范围无法确认时继续显示原始已知来源和占用，只将生活标准化指标标待核，不阻塞 I−R/E−R 的消费标准化。主报表保留总额；“标准化支出下降”不自动解释为节省。

### 6.4 分析请求、快照和结果

用户在分析页选择期间、basis、预算版本、对比窗口和问题模板，也可追加文字问题。点击“生成分析”先由应用生成 analysis_request 与不可变 input_snapshot；得到可用确定性指标后可直接阅读，再经任务进入 Codex。无 AI 时显示“指标已就绪，文字分析待处理”。不把普通页面查看自动变成模型调用。

input_snapshot 至少冻结 query、scope、period、basis、currency、data_revision、rule_version、dimension_version、budget_version、policy_version、metric_definition_version（可用计算器版本或目录哈希）、coverage_version、来源截止、metrics、明细引用／哈希及未决金额。现有月度三表快照可复用，不足字段以分析专用快照补齐；不能只存一句 prompt 或当前查询链接。

每个 metric 包含 metric_id、label、value_minor/null、unit、period、basis、coverage、带版本的 formula_id、drilldown_spec；均值保留分子／分母，比例注明零／未设处理。已记录合计与完整期间总额分开：缺覆盖仍展示已知值；只在缺失金额具有可证明上下界时给区间，否则精确剩余不可确定。已知合计不能笼统称下限，未收到的退款可能降低最终数值；各类未决金额重叠时不能相加为一个不确定总额。服务汇总全体合格事实；模型获得有限代表明细，但全量指标不受前端 200 行或模型上下文限制。

分析结果包含 findings、hypotheses、actions、questions。每条 findings 引用 snapshot_id + metric_id 或该快照中的交易版本；金额数字由服务按引用渲染，禁止把模型随手写的数字当事实。hypotheses 明确不确定原因；actions 含受影响预算项目、情景参数及模型建议。情景输入只开放预算行调整金额/倍率/生效月份等固定参数，不提供自由公式。量化节省必须绑定程序计算的 scenario_id；缺证据只提待验证建议。

结果只写 analyses，不改账本、规则、预算或预测采用版。数据／规则／维度／范围／覆盖／所选采用预算／政策／指标定义版本变化时，旧分析保留并标 stale；用户可重新生成，不自动重跑模型。仅公式定义升级也必须标过期；保存无关预算草案不使基于既有采用版的分析过期。解释正文保留生成时间、执行来源及模型标识（如可得）；不采集隐藏思维链。模型拒绝、结果无有效引用、超时或离线分别报告，不能空白伪装“没有问题”。

### 6.5 提醒

金额超出同口径预算、年度额度余量、固定期次将到期、资料过期、已知报销备忘超期由程序按规则生成。alert_id 基于类型＋目标＋期间＋规则版本，重算去重；dismiss/snooze 不修改交易。只在应用运行且新资料到达时更新，非实时监控。AI 可解释已有提醒，不另造金额阈值、不自动通知外部联系人。

## 7. 维护、数据模型与实施约束

不为本版重新建账或更换技术栈。保留既有主键、直接编辑、历史解释、凭证投影、37 科目和采用预算。通过 additive migration 增加 import_attempts/source_observations、work_items/proposals/processing_runs、analysis_requests/analyses、coverage 与版本字段；这些是逻辑职责，可按事务边界合表，不引入消息队列平台。

维表查询已完成；近期补账户、商户别名、标签和映射的受控维护。名称修正、别名合并需留历史和影响预览；科目骨架维持既定目录。只对会改变历史解释的账户范围／分类政策等使用带生效区间的必要版本；不全面套 SCD2，也不要求用户维护所有 valid_from/valid_to。当前报表用当前解释，已保存快照保留旧解释；任意历史时点重放仍不是默认承诺。

备份必须包含数据库、原件、规则配置及清单哈希，恢复需在独立目录验证、切换前备份、停写并失效旧租约。导入、撤销、投影或分析保存失败不得损坏旧事实；只有已授权的业务动作可改真实账本。本版文档交付不触发迁移、重分类或预算重算。

## 8. 交付判断

先完成“一份原生账单 → 规则 + Codex → 只处理疑点 → 当前三表/预算更新”的可演示闭环，随后扩来源、对账及完整分析；不等待所有投资、手机连接或现金预测都完成才接 AI。最低恢复可并行开发，但真实持续导入和自动写回启用前必须在独立目录演练通过。详细分期和人日范围见实施计划。

验收分开记录：①财务不变量与权限负例必须全部通过；②支持格式的解析覆盖及金额精度；③语义分类正确率与自动覆盖率，按商户类别与异常类型分层；④needs_review 是否准确召回；⑤真实 Codex 联调与用户路径；⑥真实数据只读迁移核对。金标集不使用训练／提示中重复样本冒充独立测试，不以模型 confidence 替代正确性评估。复杂关系未验收前只提供候选。

首轮可用门槛：所有支持格式样本金钱／方向／币种无静默错误，所有财务和权限负例通过；至少 100 条独立去标识或合成分类样本，覆盖短中文商户、商品反驳平台默认、人工覆盖、退款继承、综合电商不充分证据、主观标签等层；在该测试集上自动应用分类精确率目标 ≥98%，其余类型单列而不混算；同时披露自动应用数量、各层精确率和覆盖率，不将样本结果当真实长期总体错误率保证，不预设必须高自动率以避免强行猜测。该阈值是拟定交付门槛，真实模型表现待测；不满足时缩小自动白名单并重验，不能宣称已可放心全自动。
