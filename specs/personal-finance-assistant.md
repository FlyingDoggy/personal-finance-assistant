## 1. 目标与范围

构建单用户、本地优先的个人资金与交易管理应用：收齐消费和收付记录，分清消费、还款、报销、投资，维护预算与未来资金安排，提供可追溯的分析。日常操作为“导入 → 自动整理 → 处理疑点 → 看报表”，定期核对账户余额。

一期交付五类输出：账户资产与负债表、收支结余表、现金流与未来资金安排表、预算表、预实分析表。它们采用明确的个人管理口径；不以完整家庭财富核算或企业会计流程作为使用前提。

应用负责 SQLite 数据、规则、任务和确定性计算；Codex 经本地 MCP 补充分类、关联判断和分析。规则能够处理的直接处理，校验通过的 AI 建议自动应用，只有疑点需要人工。没有运行 Codex 时，导入、规则、人工修改、对账及已有数据的报表仍可使用。

### 1.1 一期纳入什么

| 对象 | 范围及最低资料 |
|---|---|
| 现金及账户余额 | 银行存款、实际持有余额的支付账户及需要管理的现金；绑定银行卡的支付渠道不重复创建资产。 |
| 投资 | 本人基金等持仓、申赎、费用、分红、已知成本及带日期的市值；没有历史成本仍可展示有证据的持仓快照。 |
| 公积金 | 已知余额、缴存和提取，标为受限资金，不计可用现金。 |
| 往来 | 工作垫付保留为费用，报销待收仅作备忘；其他有明确债权依据的应收和可退押金按需纳入资产。 |
| 信用支付与借款 | 信用卡、花呗、白条应付，确有证据的融资分期、房贷和其他借款本金；还款计划独立。 |
| 收入、消费与计划 | 已发生收入与消费、预算、固定承诺、未来收入及还款预测；实际和预测分开。 |

房产、汽车和日常耐用品不进入一期资产盘点，不要求估值、资产卡片、折旧或处置记录。普通手机、家电、运动设备购买时计消费。房贷仍然管理，但“纳入范围的资产减负债”不得称为完整家庭净资产。

### 1.2 完成标准

1. 消费与还款不重复计消费，多渠道证据和重导不重复计数。
2. 交易性质已明确的消费，即使细分类未知，也进入总消费及总预算。
3. 人工可直接修改、批量分类、标记重复和撤销修改，保留原始资料与前后值。
4. 金额与余额可核对；缺项、未知值、待解释现金变动可见，不用编造交易配平。
5. 三张管理报表与预算同源计算、可下钻、可导出，清楚说明范围、日期和完成程度。
6. 投资本金与收益分开；只提供市值快照时不伪造成本和收益。
7. 无需录入房产或折旧，无需月结或手工凭证，即可完成一期流程。
8. 可重启、换 Codex 会话、备份与恢复，不依赖长期聊天记忆。

### 1.3 当前实现与本版交付目标

当前 schema 2 已支持标准 CSV、原始证据、直接编辑与历史、已知范围三表、预算版本和明确项目关联、凭证明细、核心维表查询、冻结报表快照、适用设置与 JSON 逻辑导出。既有真实资料和已采用年度预算已迁入，历史 Excel 核对零差异。这证明迁移保持原结果，不证明所有尚未覆盖的业务已正确实现。

当前上传不会启动 AI，也没有原生格式持续导入、MCP 或 AI 分析产品。报销标准化已有纯函数但未接正式报表／预实。新合成评审还复现了双端还款、预算重复占用、缺月精确余额和报销归期等边界，须按实施计划修复，不把“有校验函数”当成可开放 AI 的依据。

本版目标是完整定义：添加账单 → 预览 → 确定规则 → Codex 补充 → 校验自动应用／疑点人工 → 三表与预算更新 → 可核对分析。F01—F15 的功能、AN-01—AN-08 的分析产品、流程、自动化权限、恢复和验收在[闭环规格](ingestion-and-analysis.md)中逐项定义；当前实现状态由[开发记录](../plans/implementation-status.md)单独维护。

## 2. 决策、默认与版本变更

### 2.1 已确认决定

| 编号 | 决定 |
|---|---|
| D-01 | 个人与家庭使用同一统计主体。 |
| D-02 | SQLite 保存统一数据，交易有科目、标签和描述。 |
| D-03 | 交易从 2026-01-01 起，不追溯更早逐笔历史；先导入已取得资料。 |
| D-04 | 已知账户包含招行借记卡、招行／中信／浦发信用卡、北京银行房贷账户、公积金、支付宝花呗和京东白条。 |
| D-05 | 信用支付需要消费侧信息，不能只从还款推造消费明细。 |
| D-06 | 需要三张管理报表、预算、预实分析、投资记录和 AI 建议；报表范围按 D-11 收紧。 |
| D-07 | 前期由 Codex 处理 AI 任务，账本和报表独立，暂不增加模型 API。 |
| D-08 | 校验通过的 AI 判断可以自动应用，只确认疑点。 |
| D-09 | 定期导入银行流水校正，AI 辅助分类、标注和关联。 |
| D-10 | 私人原件与账本保留本机；Codex 处理所需字段会进入其模型上下文，不能把本机存储理解为没有模型数据传输。本轮只修订规格，不发送真实材料或执行金融交易。 |
| D-11 | 一期聚焦账户、交易、预算、现金安排和投资；资产范围采用第 1.1 节，不要求纳入房产或完整家庭资产。 |
| D-12 | 个人管理实际采用总额口径：工作垫付全部保留在费用，报销到账记 4005 其他业务收入的“报销回款”子类型；待收仅备忘，不增加同笔应收资产。 |
| D-13 | 无需偿还的家庭赞助到账记 4005 的“家庭赞助”子类型；不与报销混合，不抵减费用，未来预算默认不依赖。 |
| D-14 | 预算用同一观察窗口内的已到账报销累计额同时抵减收入和费用，按选定自然月数平均；完整窗口优先，用户可明确选择含部分末月的估计并披露缺口。抵减采用独立汇总调整行，不改变逐笔实际、日期或消费类别。 |

用户在启动开发后进一步明确：前端在功能适用的前提下“能抄尽抄”，有源码可复用时不先自行重新设计。先判断是否符合本地个人财务需求；不搬不适用的功能或无实现的菜单。该决定优先于本版早先的“按模式重写”建议；实际复制须保留许可和固定版本来源，数据接口与财务语义的冲突须显式适配。

### 2.3 0.1 被替代的要求

| 0.1 要求 | 0.2 生效规则 |
|---|---|
| 房产、长期耐用品及累计折旧纳入基础模型 | 从一期目录与交付门槛删除；以后有实际用途再扩展。 |
| 科目或金额修改必须冲销／更正凭证 | 直接编辑、记录前后值、原子重算；真实退款另记业务。 |
| 月结、重开、跨期重述框架 | 无期间锁定；当前报表重算，已保存快照保留并标记已过期。 |
| 精细分类未定就等待入账 | 已确认消费先记未分类支出；性质不明仍待确认。 |
| 完整三表及直接／间接法勾稽 | 先交付明确范围的管理报表；一期不要求间接法或标准企业三类现金流。 |
| 设备资产购置预算及折旧预算 | 普通设备计消费预算；投资投入计划和偿债现金安排保留。 |

以上替代规则适用于主规格、任务和验收；不能继续按 0.1 的要求实施。自动付款、还款、下单、多人账套、税务申报、任意会计政策引擎及完整家庭财富估值均不在一期。

### 2.4 v0.3 的报销与预算口径变更

v0.3 取代 v0.2 的“工作垫付不计费用、回款核销 1004”默认规则。1004 编码保留，但在本次采用的报销模式下停用；报销事项、垫付、退款和回款的关系继续保留，待收金额不进入资产小计。实际费用和实际收入保留总额，预算标准化另行展示。此处“其他业务收入”“费用”和“收支结余”均为个人管理指标，不直接等同企业会计营业收入、成本或净利润，也不表示工作垫付全部属于个人自主消费。

### 2.5 v0.4 的变化

本版不新增科目、不改变报销实际口径、不重算已经采用的私人预算。新增可实施的前后端结构、界面状态、数据合同、预算占用与付款区分、AI 受控写回、仅支出分享和迁移规则。外部参考固定为提交 8bea959a5c49dd58e449571f57ef9e5bf7506bed；借鉴 15 项模式，并明确 8 项不能直接采用的实现，见[借鉴清单](reference-design-shiqingqi.md)。

预算展示继续遵守最近确认：按生活用途归组，固定／日常／年度／分期作为属性；宠物集中一组；已结束且当月无金额的项目不展示为一排零；已安排的服饰及数码消费计入生活预算，不再叠加早期的大件预留；探亲路费独立于市内交通；旅行等额外消费可使用剩余机动资金。机动资金支取会减少留存，储蓄目标不足时明确显示差额，不自动压缩其他类别来凑目标。

### 2.6 v0.5 的修订与明确取舍

1. 账单上传是应用功能；财务 MCP 是 Codex 的工具接口；执行器是启动模型的独立能力。三者分别设计和验收。先交付手动触发的真实 MCP 闭环，应用内运行器另做最小权限验证。
2. 确定性分析无需 AI，解释建议由 Codex 生成。预实、报销标准化和消费结构先交，不依赖全套现金预测或投资能力。
3. 把原生导入、两端证据去重、事项级预算互斥、期间覆盖、报销到账日期、预算草稿与采用分离列为前置修复；只接 MCP 外壳不算交付。
4. 功能缺口全部进入 F01—F15、R00—R10 和 AC-58—AC-78；已有 T01—T09 保留为业务范围索引，实施顺序以新 R 切片为准。R11 是应用内运行器的条件扩展。
5. 最低可恢复备份与持续使用闭环同步完成。保留 schema 2、历史 ID、人工判断、37 科目、采用预算；历史与新交易通过统一事实读取和关系命令兼容，不重新全量建账。
6. 本版不调整私人预算金额，不增加房产、折旧、企业月结或额外模型 API。新增方案及实施估计是候选设计，用户已确认的财务政策继续生效。

## 4. 系统结构

~~~mermaid
flowchart TD
  A[账单、订单、余额快照、人工记录] --> B[原件和 ETL]
  B --> C[来源事实、去重和确定规则]
  C --> D[当前交易、类别和账户变动]
  C --> E[性质待确认或分类待补]
  E <--> F[Codex 经本地 MCP 提交建议]
  F --> G[校验]
  G -->|通过| D
  G -->|疑点| H[人工处理]
  H --> D
  D <--> I[直接编辑和修改历史]
  D --> J[余额核对和三张管理报表]
  C --> J
  K[预算和未来计划] --> L[预实分析和资金预测]
  J --> L
~~~

原始资料、当前业务解释和派生计算分开。报表从统一的有效事实集合生成；未解释现金事实与已记账交易通过同一来源关联去重，不能由两个入口各算一次。应用不因产生待办就自动唤醒 Codex。

## 5. 最小数据合同

| 对象 | 保留内容 |
|---|---|
| 账户与科目 | 账户归属、类型、币种、是否属于现金；科目编码及启用状态。机构、卡片和产品为辅助维度。 |
| 原件与来源行 | 内容哈希、本机路径、来源、账户、期间、行定位、原始值、解析版本。原件不覆盖。 |
| 当前交易与明细 | 稳定 ID、业务性质、消费／结算日期、金额、账户、分类、标签、描述、版本、字段来源和人工覆盖值；4005 保留报销回款、家庭赞助等互斥收入子类型。 |
| 证据与关联 | 一份证据可支持交易组成，多份证据可支持同一交易；重复、退款、还款、报销及转账关系有类型和金额，不混用。 |
| 报销备忘 | 报销事项、已知垫付／退款／回款关联、申请及预计回款日期、已知待收和未知尾款；独立于资产账，不生成 1004 余额。 |
| 修改历史 | 对象、操作者、时间、前后值、原因（金额／性质变更时）、来源和版本。普通改类不要求长篇理由。 |
| 派生账户变动 | 交易版本及模板生成的当前分录；可重建，替换时不让旧新版本同时计入。 |
| 余额与对账 | 外部快照、日期、余额定义、可重算余额、差额、覆盖范围。外部观察不自动变成补差分录。 |
| 规则与 AI 待办 | 规则版本、必要上下文、建议、依据、未决项、租约／版本、应用结果。 |
| 预算与计划 | 原始／修订预算、情景、计划金额及日期、与实际的关联；标准化观察窗口、选定自然月数 m、覆盖状态及估计假设、报销回款累计 R、月均估计、汇总调整行和采用版本；不产生实际收入或资产。 |
| 投资 | 产品、账户、份额、交易、成本依据、正式净值及日期、持仓快照；已实现与未实现计算来源。 |
| 债务计划 | 合同、已知本金、利息／费用、到期安排；账单应还、全部欠款和未来本息不是同一数值。 |
| 快照与覆盖 | 数据修订号、规则／预算版本、截止日期、来源缺口、旧输出是否过期。 |

这些是逻辑职责，允许合并表，不要求事件溯源平台或每个对象独立服务。没有 AccountingPeriod 月结实体或通用固定资产引擎。

金额用整数最小货币单位，份额／净值／汇率用精确十进制；禁止二进制浮点累计。保留原币及人民币结算额，实际结算额不被日后汇率覆盖。拆分总额必须相等，舍入规则明确。源交易 ID 仅在来源和账户范围内唯一；同日同额同商户不自动视为重复。未知值与已确认零分开。

## 6. 轻量 ETL 与事实识别

1. 经应用上传指定文件，保存原件、哈希、来源及覆盖期间；迁移脚本可有显式目录输入，普通 UI/MCP 不接受任意本机路径。
2. 解析账户、日期、方向、金额、币种和来源标识；格式错误行隔离，不静默填零。
3. 识别同文件重导、同源重复及跨来源同一事实；金额日期相似只提供候选。
4. 应用确定规则，区分业务性质和消费细分类。
5. 明确消费可按未分类支出立即记录；未完成的类别／标签异步补充。
6. 性质或关系有歧义的保存待办；已知唯一收付事实仍可展示，不能造收入／费用配平。
7. AI 或人工补充后重新校验，原子应用，更新覆盖和报表。

一个批次可部分成功，一项业务及其关联、账户变动和处理结果必须原子提交。重新导入或解析不能覆盖人工修改。上传、预览、开始处理、AI 触发、批次计数及恢复按闭环规格第 3 节；解析尝试和来源记录身份分开，未知模板仅提候选。

| 来源 | 必须区分的事项 |
|---|---|
| 借记卡／支付账户 | 真实余额账户与绑卡支付渠道；观察余额与按流水计算余额。 |
| 信用卡／花呗／白条 | 消费、退款、还款、费用、已出账应还、未出账和分期剩余本金；只有还款不能生成消费。 |
| 订单／平台明细 | 可用于补充已有银行交易用途，不默认增加资金流。 |
| 公积金／房贷 | 余额快照、缴存提取、本金利息；不能从月供推余额或从余额差猜薪酬。 |
| 投资 | 实际持仓／成交与公开净值不同；成本未知不当零。 |
| 旧 Excel | 实际、计划、预测、备注分别迁移；旧预测结果不能当实际。 |
| 人工 | 明确是人工补充，随后可关联正式流水，不重复创建。 |

## 7. 科目与业务政策

### 7.1 科目目录

完整编码、用途、余额方向和辅助维度见[科目目录](chart-of-accounts.md)。内部保留五类共 37 个条目：资产 9、负债 5、系统范围净额 2、收入 5、费用 16。其中 35 个为业务／派生计算科目（含本模式停用的 1004），另 2 个仅用于有证据的期初或范围变更；它们都不是要求用户逐笔挑选的操作项。0.1 的 34 组是未拆开的概念范围，与这里的编码叶子数量不能直接比较。

默认 UI 展示业务性质与 16 个消费类别，账户由来源映射；收入及往来按对应业务入口填写。系统范围净额不可由 AI 或普通分类自由写入，不可用来补差。当期／累计结余是计算行，不增加独立手工科目。

类别不要求越细越好。健康／宠物、文娱／学习／运动等可用子标签分析；银行、卡片、商户、订阅频率和合同都不新增总账科目。日常／特殊、计划内外、冲动／非冲动／未知等行为标签可选，主观含义以用户定义为准；多标签不重复加总金额。

### 7.2 关键业务

| 业务 | 当前处理 |
|---|---|
| 普通消费 | 购买时确认费用，借记卡减少现金，信用支付增加结算应付；普通耐用品也按此处理。 |
| 未分类消费 | 性质明确、金额账户可靠时记未分类支出，计总消费与总预算；后补类别只迁移分类。 |
| 未知性质收付 | 保留来源事实及未解释现金变动，不擅自认定消费、借款、内部转账或应收。 |
| 信用支付还款 | 减少明确的结算应付及现金，不再次记费用；已知偿债无需逐笔配完原消费才可展示。 |
| 真正融资分期 | 依合同确认融资本金；设备购买仍一次计消费，后续本金偿还不再计费用，利息单列。未来应付利息不计现有本金。 |
| 本人现金互转 | 两端关联，合并现金流剔除。跨日使用在途须有本人归属及去向证据，不能从同额记录猜测。 |
| 真实退款 | 独立退款事件关联购买，按实际退款日期减少原费用／应付，支持部分和多次；还清后形成溢缴款，提回银行才增加现金。 |
| 工作垫付及报销 | 垫付按实际用途全部计费用，类别未知时用未分类支出；到账记 4005 其他业务收入／报销回款。待收仅备忘，不在费用保留时再累加应收资产；分次回款更新备忘关系。拒报更新备忘及预测，不再重复记费用；原先错判则直接编辑。 |
| 其他应收 | 有明确可收回依据、且不属于工作报销的款项按对应往来记录，如借给他人的本金；收回核销资产，不计收入。不得借此绕过报销待收仅备忘的规则。 |
| 押金 | 有可退依据时记押金资产；退还不计收入，实际扣除时按证据转费用。 |
| 工资与公积金 | 有工资单时以工资及单位公积金确认劳动报酬，个税／个人社保为费用，个人公积金转资产；与到账及缴存关联不重复。 |
| 只有工资实收 | 可按已确认的净额工资使用，显示口径；不强制先补工资单。后补明细替换该业务的派生结果，不叠加第二份收入。 |
| 公积金余额／提取 | 有证据余额可先展示；提取为受限资金转现金，不是收入。仅有快照差额时不自动猜缴存、利息或工资。 |
| 房贷和其他借款 | 已知本金单列负债；本金还款减债、利息计费用。本息未知时现金付款照实显示“本息待拆”，不猜拆分。无需配套房产记录。 |
| 订阅 | 已购买的月／季／年订阅在购买时一次计消费；预算按预计续费时点安排，不建立自动摊销。 |
| 未履约预付等范围外事项 | 明确保留待处理及金额，不强塞消费或其他应收；如实际资料需要再扩展专门政策，不预建通用摊销引擎。 |
| 家庭赞助／借入 | 明确无需偿还的实收记 4005 其他业务收入／家庭赞助；有偿还义务记借款。家庭赞助不抵减费用，未来预算默认不依赖；额外情景须明确假设。 |

### 7.3 现金事实与用途

现金范围默认包括现金、银行、有余额支付账户及证据明确的内部在途；不含公积金、信用支付溢缴款和基金持仓。投资账户内的现金如纳入现金范围，应单独列明，不能又包含在持仓市值中。

实际现金表按业务类型列消费及工作垫付付款、工资、报销回款、家庭赞助、信用还款、退款提回、其他往来收付、投资申赎与分红、借款收付及本息、公积金提取等。每笔资金变动只计一次；本息子项是还款总额的组成，不能再与总额相加。报销保留先垫后收的实际日期和资金占用，不以预算月均抵减替代真实现金流。普通还款可补原消费关系用于分析，但一期不要求按每笔消费追溯经营／投资用途。

已去重且账户、金额、方向确定的银行收付，即使性质未知或本息未拆，仍进入“未解释现金变动”或“本息待拆付款”。该展示不产生虚构平衡分录。补齐性质只迁移分类，不新增现金。来源记录与派生分录通过同一事实 ID 取一次；跨来源疑似重复未解决时保留缺口，不冒充完整合并现金流。

未经过现金账户的信用购买、直接商户融资、工资扣缴、红利再投与估值变化不虚构现金收付。历史实际和未来预测分栏，绝不把预测计入实际期末余额。

## 8. AI、自动处理与疑点

AI 可补类别、标签、说明、关系和解释，不要求处理所有交易。已确定规则可直接运行；类别待补不阻断消费统计。新 AI 判断不必先命中旧商户规则才自动应用，但必须提供可追溯依据。

2026-10-27 分类补充：先使用用户逐笔确认，再看明确商品／服务说明，其次使用用户商户默认规则和有依据的商户语义；不能只依赖少量关键词而把明确用途留作未分类。已有支付宝商品说明可按日期、金额、付款卡和银行双向唯一关联，跨日最多两天还须完整商户一致；只补证据，不新增第二笔费用或现金。盒马、沃尔玛／山姆、7-11、果蔬好等食品超市／便利店默认餐饮，MUJI／宜家默认日用居家；明确的保洁、宠物或其他商品按实际用途。用户已确认美团／汉海／三快相关消费默认餐饮，明确其他用途除外；纯支付通道和无商品明细的综合电商不能通用推断。稳定商户的同类商品可供用途推定，但须标明是商户参考而非本笔订单匹配。退款继承已关联原单的当前类别，原单改类后同步；类别变化不得改变金额。已确认的车辆月租从历史可变消费基数中剔除，按固定安排排期，避免重复预算。

输入为必要记录、候选关联、当前版本、规则及已确认相似案例；不默认提供完整账号或全部历史。进入 Codex 的字段会进入其模型上下文，本地保存不表示选中字段不经模型服务。账单备注和文件文本是数据，不能作为改变权限的指令。

| 校验 | 要求 |
|---|---|
| 结构与版本 | 有效类型、科目、金额及引用；对象未被人工或其他批次更新。 |
| 证据与关系 | 金额日期账户有来源；去重、转账、报销等关系有业务依据；单纯同额或高置信度不够。 |
| 金额与状态 | 不重复使用业务金额，不超额分配，不将预测写实际；已明确业务模板的分录平衡。 |
| 人工优先 | 不静默覆盖人工字段、启用长期规则、改变预算或统计范围。 |
| 原子提交 | 幂等键、预期版本和有效任务租约在同一事务内检查。 |

校验通过排除的是已定义错误，不代表系统能证明全部语义正确。分类错误可以直接改。疑点分成金额／性质阻塞、关联待核、类别待补、辅助标签未知和资料缺口，不把所有情况都变成逐笔审批。

疑点页显示原记录、建议及依据、影响金额，支持直接填写、拆分、选择候选、同类批量处理和延后。修改一笔不自动升级成永久规则；启用同类规则由用户明确选择。

## 9. 直接编辑、历史与恢复

### 9.1 编辑语义

| 操作 | 系统行为 |
|---|---|
| 改类别、标签或描述 | 更新当前业务版本并记前后值；类别报表更新，金额及资金事实不变。 |
| 改金额、日期、账户或业务性质 | 保留原始值与人工覆盖值，检查退款／还款／报销等关联，原子替换当前派生结果；有关余额需重新核对。 |
| 标记重复／合并 | 保留全部来源；仅一份有效业务计数，重复来源继续识别，重导不复活已排除业务。 |
| 排除非交易记录 | 标记原因及原记录，不硬删除原始资料；排除一笔真实交易的影响须可见。 |
| 撤销修改 | 以新版本恢复选定前值并重新校验；不能绕过后来新增的关联和金额约束。 |
| 真实退款或后来拒报 | 新增实际发生的事件及日期，保留原交易，不能通过改原金额隐藏后续事实。 |

已入账交易仍可直接修改，不要求冲销单、反向交易或重新录入一整笔。账务行可以在事务中替换，修改历史保留前后值及来源，不能让两个有效版本共同计数。关联冲突时提示需要重新分配的部分，不能静默丢掉关系。

消费发生日、银行入账日和实际结算日是独立字段。只修正消费日只影响消费及负债的对应期间，不能自动移动已有付款或还款的现金日期；修正实际结算日必须有对应收付依据。修改操作显示它影响的是哪个日期。

### 9.2 报表与计算影响

没有强制月结或期间锁。历史修改更新当前视图，已保存／导出的旧报表保留原数值和版本并标记已有更新；AI 旧分析同样标记过期。原始预算不因实际修改而改变。

一般消费修改只重算受影响汇总与对账。投资历史成本或份额修改必须按日期顺序重算其后持仓、处置和估值；完成前受影响收益显示待重算。该要求不扩展成通用月结重述框架。

### 9.3 原子性与并发

同一请求 ID 与相同负载重试返回相同结果；相同 ID 不同负载拒绝。不同 ID 也不得绕过去重生成同一事实两次。事件更新采用预期版本，过期 AI 结果不得覆盖人工修改。

任务领取有到期时间与令牌，重新领取更换令牌，旧执行者提交被拒绝。数据库事务中统一提交交易版本、关联、派生结果、历史和操作结果；模型等待不占写事务。客户端超时可按请求 ID 查询，重启后恢复任务。简单本地任务表即可实现，不需要独立队列服务。

## 10. 余额核对与覆盖

按“账户＋币种＋日期＋余额定义”核对。账单应还、全部未偿本金、未出账和未来计划不得直接相减。已知期初加期间变动应等于相同口径期末；外部快照、按已处理业务重算的余额及未处理差额分列。

有某日余额即可从该日开始核对；没有 2026 年初余额不阻塞当期使用，只限制历史余额计算。不能为对齐外部余额自动生成其他收入、费用、应收或范围净额调整。已知一笔本金变化但未知贷款期初时可记录该笔变化，绝对贷款余额仍未知。

账户设置提供带生效日的范围加入／退出及期初入口，保留证据和范围版本。加入一个此前已存在的余额不是当期收入或现金到账，退出也不是费用或债务豁免。现金流期初期末比较须使用相同账户范围；改变范围导致的差额单列范围影响，资料不足时不宣称已完成现金勾稽。

覆盖按来源、账户、期间显示已收到、解析失败、已处理、待解释、已对账及缺口。没有记录与确认无交易不同；资料缺失与零不同。账户余额对上不表示消费类别都已完善，类别完善也不代表全部来源齐全。

## 11. 三张管理报表与导出

### 11.1 账户资产与负债表

列明纳入账户、现金、投资、公积金、其他有依据的应收和押金，以及信用应付、融资、房贷和其他债务。工作垫付已保留费用，其报销待收只在备忘区显示，不进入资产或范围净额；1004 在本模式下停用。资产范围采用第 1.1 节，不显示房产、设备和累计折旧的待补任务。

每项显示来源时点及是否可由流水重算。可重算账面与仅有外部快照的观察值分列；持仓有市值无成本仍可展示已知市值小计，但不能制造成本、收益或用期初范围净额填缺口。同一投资的成本和市值是两种计量列，不是两项资产。

同范围同日期资料足够时可计算“纳入范围净额＝资产－负债”；不叫完整家庭净资产。未知账户、旧快照和不一致时点明确提示，只报已知小计。尤其房贷纳入而房产未纳入时，说明此净额不衡量家庭完整财富。

### 11.2 收支结余表

按确认月份列劳动收入、已实现投资损益、分红利息、4005 其他业务收入，以及消费和其他费用；结余＝这些收入－费用。4005 下分别显示报销回款、家庭赞助等子类型，报销按实际到账月份确认。未实现投资估值变化另列，不混入日常收入预算。需要总变动时以“结余＋未实现变动”另行展示。

信用购买及工作垫付在发生时计费用，还款不重复；报销到账计上述个人管理收入，借款和投资本金回收不计收入。真实退款仍按退款日期冲减原费用，不当报销回款。普通耐用品和订阅一次计消费，未分类支出计总费用。总额口径包含工作垫付，不能直接称为纯个人消费或企业净利润；标准化预算口径按第 12 节另列，不能改写实际交易。工资采用净额或明细口径时显式标注；比较期间混用口径时提示限制。

### 11.3 现金流与未来资金安排表

历史实际按第 7.3 节，明确来源事实、用途和待解释金额，保留账户级收付及合并视图。期初现金＋净变动＝期末现金只在相同范围、期间覆盖充分时验证；外币折算影响如有须单列，不能当收入或消费。

未来部分从已知现金基点、固定承诺、预计收入、报销及债务计划计算情景余额。预计报销、奖金等不确定项标注假设，可分别启用，不作为已到账；家庭赞助默认不进入基准情景。报销预测使用有依据的预计回款日期及金额，不能把 R/m 当作每月固定到账；单列先垫后收的周转风险、未知尾款、跨年待收及回款延迟情景。实际发生后关联对应计划，预测剩余部分扣除已发生额，避免同一付款算两次。

### 11.4 一致性边界

- 已明确业务的内部借贷平衡，但不以此宣称资料完整。
- 同范围完整资料中：期初范围净额＋收支结余＋单列未实现估值变化＋有证据的范围加入／退出＝期末范围净额。没有足够资料时不显示通过。
- 现金观察已去重但性质未定时可展示实际收付；不因此声称其损益、债务或全账勾稽完成。
- 不要求间接法现金流或手工结转当期结余。
- 页面和 Excel／CSV 使用同一计算，带数据修订号、截止日期、统计范围、来源时点、覆盖及预算版本，可下钻至当前交易和原件。

## 12. 预算、预实与 AI 分析

### 12.1 实际总额与预算标准化

收支实际按确认月份保留总额，工作垫付不逐笔剔除；真实退款按退款月份冲减费用。未分类支出计总费用，并显示尚未分配到类别的金额。普通设备购买进入消费预算，不再建立重复的资产购置预算。投资投入计划和还本现金安排独立，汇总资金需求时同一事件只计一次。

预算参考窗口优先采用资料完整的自然年度或滚动 12 个月。设选定的同一观察窗口包含 m 个自然月，原始收入为 I、费用为 E、4005／已到账报销累计为 R，则标准化收入 `I* = I - R`，标准化费用 `E* = E - R`，标准化结余 `I* - E* = I - E`。收入、费用与 R 必须采用同一窗口；原始和调整后收入、费用的月均均除以 m，不用某几个月的报销抵全年费用，也不按各项目有交易的月份数分别求平均。完整而零回款的月份计入 m；缺失资料不能默认为零，部分月份不能标成完整月份。

用户明确选择包含部分末月的观察窗口进行估计时，可把该末月计入选定自然月数 m。仅汇总窗口内已观察的收入、费用和全部已到账报销，统一按 m 平滑，不按天数补足末月、不生成缺失交易；输出须保留 `partial` 状态、观察截止及来源缺口。当前用户选择 2026 年 1—10 月窗口，三项累计数均除以 10；10 月尚未完整，不能把该结果称为完整十个月的历史月均。

月均抵减额为 R/m，全年参考额为 12×R/m；不因集中回款而对最近月份加权。同一窗口内的已到账报销无需逐笔拆回早期月份后才能参与估计，实际到账和费用日期保持不变。月均只用于预算标准化，不证明每月都会回款。部分末月可能低估月均费用；跨年回款、已知待收、未知尾款和垫付与回款错位对调整后消费的影响方向不确定，应披露而不补造归属，不能据此声称逐笔费用已精确剔除或完整净消费已知。

报销抵减在收入、费用两侧各设独立汇总调整行，不能伪造逐笔报销归属、平均摊到各消费类别或改动原交易。家庭赞助不属于 R、不抵费用；未来基准预算默认不依赖家庭赞助。未来工资已单独排除报销，不能再从工资扣 R/m；历史总收入扣 R 与未来工资设定是不同步骤，不重复扣减。

### 12.2 预算生成与采用

下一年预算基于已知实际，结合日常基线、一次性事件、可控因素、订阅及债务到期、收入变化和用户计划。先在汇总基线抵减报销，再对标准化后的可变消费基线应用缩减倍率；不能先按倍率压缩含垫付的基线再减全额报销。固定承诺与其他独立计划保留依据，汇总抵减不自动证明某类别或固定／可变部分的逐笔归属；该划分资料不足时披露预算假设，不按比例硬摊。缺少月份不当零，年化及补充假设标出处。行为标签不完整不阻塞预算，只降低相应解释的确定程度。

采用预算时冻结参考窗口、m、R、月均估计、汇总调整行、缩减倍率及其他假设。保存原始已采用预算、独立修订预算和滚动预测；后续回款或历史补录不能改写已采用估计，修订另存版本。AI 可建议，用户决定采用；实际更新不回写原预算。

### 12.3 预实、提醒与解释

预实同时保留原始实际和标准化实际，注明各自窗口、报销调整及所比较的预算版本；标准化计算不能覆盖原始报表。费用偏差＝实际－预算，收入偏差同式但含义不同；只在同一口径下比较。分开解释真实费用变化、报销回款时点和估计变化，不能把集中报销、少回款或新估计导致的标准化金额变化称为消费节约或超支。零预算与未设预算分开，均不输出无意义比例。多标签切片不重复累计。退款另可看原消费归因，纠错按修改后的实际日期重算。

未来收入预算采用劳动收入、已实现投资损益、分红利息及其他有依据收入的假设，报销通过上述标准化及独立现金安排处理，家庭赞助默认不纳入基准；未实现估值不计执行率。规则可提示超预算、订阅重复、报销备忘待收逾期、其他应收逾期、未来现金不足及资料过期；AI 引用报表和交易解释事实、推断、假设与建议，不能自行改预算或执行投资。提醒时效受导入和运行频率限制。

### 12.4 面向个人的月度预算展示

默认预算表采用“生活用途 × 12 个月”，包括住房与居家、交通与用车、数字与通信、餐饮、购物与个人生活、健康与健身、宠物。同一用途的费用集中展示；固定、临时、年度均摊、分期以及确认状态是项目属性，不再把同一用途拆到“固定／日常／专项”三个区域。显示分组映射到现有科目或子标签，不据此新增总账科目，也不改动历史交易分类。

历史消费形成的分期仍独立显示，主表每笔只列还款本息，支持页保留本金、利息和剩余期数。无法确认用途的合并账单分期不猜测分入今年餐饮、购物等预算。健身等新计划按选定还款排期计入健康与健身，不同时再扣课程价格或课程月均。

月度预算安排与逐日现金预测分开。预算里可用年度均摊额度表示疫苗、绝育等项目，但应标明均摊及付款日期未知，不称为当月已经支付。物业、取暖、年付订阅仍按已知月份安排，不能因展示合并擅自改变金额或排期。预实比较须采用匹配的预算口径；历史实际日期和负债记录仍保留。

当前用户选择 Codex 按已确认的月费、全年 12 个月安排，不额外预留 12 月账单跨年付款。两只狗的生活、保险、疫苗和绝育统一在宠物组。旅行、大件和冲动消费使用生活预算后的机动资金，不再添加旧版独立大件预留或把支取示例混入主预算。机动资金是预算后可安排的余额，池内消费减少最终留存；它不替代账户余额与负债核对。

汇总只累加各用途小计与历史分期一次，不把项目、组成项、小计、年度目标和参考月均一起相加。重分类不改变金额；取消或调整额度应有用户依据并保存预算修订版本。

### 12.5 三种计量必须分开

“预算实际”不能无条件等同费用表金额。界面默认提供生活资金安排，另可切换消费发生分析和真实现金预测。

| 计量 | 事实与时间 | 用途 |
|---|---|---|
| 消费发生 | 按第 7 节确认日汇总收入／费用，分期购置保留全额消费 | 收支表、历史消费分析、消费口径预实。 |
| 生活预算占用 | 根据预算行的执行规则，从消费事实或特定付款事实归集；每个有效事实只进入一个主用途预算行 | 判断本月／全年额度是否够用。信用卡普通新消费购买时占额度，之后还款不再占一次。 |
| 现金实际与预测 | 实际按现金账户收付日；未来按到期计划、付款渠道和已知账单预测 | 判断某日是否有钱付款，不以预算月均冒充银行扣款。 |

预算行必须记录 execution_basis：

- **consumption**：普通新消费按发生额占用。后续信用还款不会再次扣同一消费额度；退款按实际退款日释放额度，并可查看原购买归因。
- **scheduled_payment**：明确的历史分期、房贷及采用按期付款预算的新融资事项，按履约付款占用；同一事项的原购买额不再进入生活预算占用，但仍在收支表计全额费用。付款本金、利息合计只扣一次。
- **annual_envelope**：年度额度按月作资金安排，实际购买占用年度额度；月度均摊不生成已付款记录。既可按消费发生占用，也可按明确付款事实占用，须另设 actual_basis=consumption 或 payment，不能混用两者。

例外选择须按明确的事项／合同 ID 生效，不能把全科目消费粗暴排除。无法唯一映射的有效消费归入“待分配预算占用”，进入总占用而不冒充节省。已确认是普通日常消费、仅细类或预算行不明时，同时计入 U_daily,m，先扣首页日常总额度，分配后不再扣一次。如果它是否属于年度／按期事项、或是否已包含在已知履约额仍不确定，显示总占用及日常剩余的区间和待确认金额，不给单一精确剩余额。

### 12.6 预算字段、额度与目标公式

预算版本记录年度、币种、状态 draft／adopted／superseded、原版 ID、参考窗口、政策版本、资金来源假设及目标。采用版不可原位修改；调整产生修订版，界面明确选用哪一版。滚动预测不成为另一份已采用预算。

每个预算行至少有稳定 ID、用途组、显示名称、执行口径、来源计划／事项、月份金额、付款日期或日期未知、确认程度、是否固定、年度额度和分配方式。金额为空代表未设，不等于零；已知零表示本月没有安排。

对选定月份 m：

- A_m：预算口径可用资金来源，包括已设定的净工资及明确启用的其他可用来源；公积金提取必须标“资产转入资金”，不能改称收入。
- F_m：确认的固定安排及历史分期。D_m：已设置的日常、购物和年度额度月分配；两者为互斥归集。B_m = F_m + D_m 为本月全部资金安排。
- U_m：按行执行规则累计的当月实际预算占用。V_m = B_m − U_m 仅为“当月安排与发生差额”，可负；年度项目集中支付会改变它，它不是首页可花额度，也不自动触发超预算。
- S：用户设定的年度留存目标。P = ΣA_m − ΣB_m 为预计预算留存；目标缺口 G = max(0, S − P)。它是计划结果，不能因为目标设得更高而自动增大 P。
- 用户选择平均分配目标时，S_m 为按分确定性分配的月目标，全年合计恰为 S；目标下生活额度上限 = A_m − F_m − S_m。负值直接显示资金不足，不裁成零。逐月不均匀目标允许另设。

首页分列“本月日常剩余”“固定及历史分期待付”“年度项目剩余”，并给出“为达到目标还需调整多少”，不把这些数混成一个可任意消费的余额。设 R_m 为 D_m 中年度额度的月分配，U_daily,m 为本月普通日常／购物行的实际占用，则本月日常剩余 L_daily,m = D_m − R_m − U_daily,m。固定行按各行计划与履约计算待付；年度行按全年额度减累计占用计算剩余，不再从日常剩余扣同一笔年度付款。各行仍在原生活用途组内，不把宠物等拆到多个展示类别。

预算行要明确资金归类 fixed／daily 与周期方式；年度额度的月分配统一属于 D_m，已知指定付款月的固定费用可属于 F_m。年度额度仅为用途约束及资金安排，不证明已划拨到独立账户或已有现金；实际付款能力仍看现金预测。“预计预算留存”不是完整家庭净资产增加：其中若有公积金提取、既有资金动用，需列来源说明；投资内部转账不是支出，借款不是可持续收入。

净工资与费用需要桥接：A_m 默认只取预计可到账净工资，实际资金来源只取同一工资事实的真实净到账。补工资单后，账面劳动收入可包含税前薪酬和单位公积金，但已扣税、社保和个人公积金等不再占生活预算；相关费用仍保留在收支表。该排除必须关联工资事实及扣缴证据，标记 source_already_netted，不能将整个税费／社保科目一律排除。另行银行缴税、补缴社保等未包含在净工资里的实际支出照常占用适用预算。缺扣缴明细不反推，不因补单改变原净到账及既有生活留存。公积金账面缴存不是到账可用资金；已明确选择的提取才作为资产转入来源，禁止又从完整劳动收入加一次。 对已纳入该预算资金来源政策的公积金动用，先提至银行再还贷、直接划给贷款两种路径采用相同留存计量：已证实用于还贷的金额计一次资产动用来源，实际偿债全额计一次履约占用。直接还贷不生成银行现金事实；须有公积金扣减及贷款履约依据，不能仅据计划假造来源。未启用公积金来源时，两种路径均不加 A，单列资产动用说明，不能按支付路径选择性增减留存。

实际目标进度采用已采用版本的资金留存计量：累计合格实际资金来源减累计生活预算占用；仅现金互转不计来源，投资本金投入不计消费，未支付普通信用消费仍占用，计划额度本身不当实际支出。生活预算个人标准化模式下，先从有效占用去重汇总，按闭环规格第6.3节声明A_gross/U_gross/R_scope与事项范围；只将确已纳入来源基数的适用报销两侧同额抵减，不能一侧净额一侧总额。来源本已排除报销时不再扣一次；范围不明只暂缓生活标准化指标，消费口径I−R/E−R仍按全部同窗到账报销计算且无需逐笔匹配。年度均摊还未支用的部分另列“已安排未支用”，不宣称可随意消费或永久攒下。存在已发生未取得明细的信用消费、未解释资金或覆盖缺口时，实际进度标为 partial，并显示可知范围。

本版本不承诺从不完整余额反推出真实年度储蓄。实际进度、预计全年留存、目标和当前现金余额为四个不同指标，均带 metric_id、basis 和覆盖状态。

### 12.7 全年排期、付款替代与年度预留

周期计划按所选年度完整生成 12 个月视图，支持月、季、年、指定日期、起止期和不等额尾期。生成 occurrence 的唯一键为计划 ID＋计划版本＋期次；采用新版本时替代未履约的旧 occurrence，已关联实际仍保留。提前一年生成的仅是计划，不入实际交易。

实际付款通过 plan_actual_links 按金额分配到计划期次；有实际证据才确认履约，支持部分支付、合并扣款、提前还款、撤销错配和退款重算。到期、银行匹配候选或 autopost 配置均不得凭空生成实际。剩余预测 = 计划应付 − 已确认履约；超额付款单列差异，不让剩余变成另一笔负付款。

年度项目可选择指定付款月或年度额度月分配。月分配尾差由最后一个分配月承担，全年守恒。年度额度下的购买与预留是同一预算行的实际和计划，不再增加一个专项支出行。付款日期未知时不伪造日期，现金预测给区间或“日期待定”提醒；年度余额采用“全年额度－累计实际占用”，月度资金节奏另列。

退款按原事项的执行规则处理：consumption 及 actual_basis=consumption 的年度行，按已确认退款在退款期冲回占用；scheduled_payment 及 actual_basis=payment 的年度行，仅释放有证据已经返还的履约金额。商品退款抵掉未偿本金、取消未付款或免除未来利息时，只修改相应负债与未履约计划，不能把未付部分当已用额度退回。手续费不退时保留原费用及占用。无明确返还／债务抵减分配时标待核，不能凭商品退款总额自动释放额度；跨年退款按退款期展示，原消费年度归因另列。

新增分期的起始月、期数和总费用是合同／计划参数。总利息暂估且未有实际账单时可生成每期付款预算，但必须标估计；不能把未来总利息计入已欠本金或当期实际费用。实际账单到达后修订未履约计划，保留已采用预算及差异解释。

### 12.8 防止预算、信用卡账单与现金计划重复

消费行和融资事项带 funding_group_id，账单付款经金额分配关系连接一个或多个资金事项。生活预算对每个消费／履约事实按所选规则计一次；同一账单中的多笔合法消费不能因共用付款端而只保留一笔。现金预测取实际现金支付端一次，不能再叠加对应消费预算额。信用卡账单内已涵盖的消费和分期，纳入账单一次，不再作为额外银行付款；账单未涵盖部分才另排期。

有明确账单及到期日时据此预测；没有账单时可依已知信用消费和账期生成估计，标记来源和缺口。连付款渠道都未知的未来消费列未分配资金需求，不能给出精确的逐日余额。未知起始现金只能计算净变动，不填零推绝对余额。

预实接口明确区分 consumption、living_budget、cash 三个 basis。切换口径只切换视图，不改原始数据；图表、明细、导出及下钻必须沿用相同 basis。月度限额进度提醒不用于把全年额度项目在实际付款月自动判成超支。

### 12.9 分析产品与当前实现边界

[闭环规格第 6 节](ingestion-and-analysis.md)定义数据健康、消费结构、大额／事件、预算目标、报销标准化、固定承诺／现金、复盘情景、投资复盘八项分析。每项明确入口、事实指标、计算口径、AI 作用和缺数据时的展示。

指标需要期间级、basis 级覆盖；不得用“一年有一笔已关联实际”让全部月份显示精确余额。保留已知累计数，缺少完整证据时显示缺口／区间；完整零交易月才能为零。预算去重须在经济事项层对 consumption 与 scheduled_payment 互斥，不能只查 usage.id 是否唯一。报销收入及 R 按已证实到账日归期，消费日与现金日可以分开不代表所有收入性质都允许任意分开。

当前保存预算即新增当前版本的实现须补 draft/adopted/superseded：草案和 AI 情景不能成为首页当前采用版。财务快照及分析冻结指标定义／政策、范围覆盖、规则、维度、预算、指标定义和数据版本，公式升级也可使旧分析过期。此节是需实现的修复合同，不声称当前代码已经满足。

## 13. 投资记录与收益

按投资账户＋产品记录申购、赎回、份额、费用、分红及正式净值，默认移动加权成本；买入费用计成本，卖出费用扣处置收入。已实现收益＝处置净收入－对应成本。现金分红单列；红利再投记录分红及份额增加，不虚构现金。

期末未实现余额＝市值－剩余成本；期间未实现变化＝期末余额－期初余额，包含卖出时转出的原有浮盈。与已实现收益合计时不能把旧浮盈再算一次。成本和净值有证据时可自动计算或物化当前估值调整，不要求每次生成不可变凭证链。

只有持仓快照时允许先用，标明时点、已知市值与成本缺口；不能用期末减期初直接叫投资收益，必须区分期间申赎和资金进出。成本未齐不计算已实现收益，缺完整日期与资金流不输出个人收益率。投资账户现金与持仓市值去重。

本金投入、回收、已实现收益、分红与未实现变动分别展示，计划与成交分开。手工／文件导入是一期必备闭环；外部金融 MCP 可选。前轮研究的东方财富妙想和盈米／且慢可作为候选，天天基金本人持仓及交易读取能力尚未核实，接入前再验证授权、费用、覆盖与时效。

### 14.2 交易详情与金额说明

详情默认按“业务解释 → 金额影响 → 证据 → 修改历史”展开：

1. 商户、商品或描述，消费／入账／结算日期，账户与支付通道，业务性质、用途、标签。
2. 原始文件金额和方向原样显示；旁边注明来源规则，例如“本账单正数表示信用卡消费”。不要求用户理解借正贷负。
3. 规范金额列：计入收入、计入费用、现金流入、现金流出、预算占用，均有币种、日期和 basis；无此影响显示“不计入”，金额未知显示“待确认”，不能都显示 0。
4. 高级展开显示账户净变动、负债变化与派生分录；原币金额、人民币结算额、估算汇率不混为一列。
5. 一条消费有多份证据时，明确“银行证明收付／订单补充用途”，点击可见来源行和本机原件。

导出的明细表保留独立原始列、收入列、费用列、现金流入／流出列及说明页。报表金额使用业务语义：费用正常为正、退款冲减费用为负；收入正常为正；现金净额正为流入、负为流出。账户变动与这些列不可直接求和。

### 14.3 复核、编辑及批量操作

每个疑点返回 reason_code、说明、证据、候选、受影响指标与金额。优先处理会改变收入／费用／现金的性质和重复疑点，再处理类别，最后是可选行为标签。已明确消费可在总额中出现同时仍挂类别待办。

用户可保存本笔修改，不必同时创建规则。批量动作先显示选中数量、共用条件、可能影响的总额和排除冲突项；同类是可解释条件，不是只凭 AI 相似度。每项业务原子处理，独立多笔可部分成功，但返回每笔结果和重试入口。拆分、去重合并及同一事项关联属于一个原子业务组，不能部分成功。

界面保存中禁止重复触发；网络超时按 request_id 查结果。服务未确认前显示“保存中／待查询”，不能先以成功样式承诺金额。普通只读图表可即时筛选；财务修改不采用无法回滚的乐观余额。

### 14.4 预算手机视图和展示政策

默认单月卡片显示用途小计、已占用、剩余、固定安排与待付款；年度视图仍可横向查看 N×12。分期支持展开剩余期数、每期本息及证据，默认不把本金利息分成两条生活支出。宠物生活、保险、疫苗及绝育统一在宠物用途组，健康与健身另组。

分类科目与展示用途分开：16 个费用科目不随预算排版增加；用途映射可把多个科目／子标签放进同一组，但同一事实的主组唯一。分类尚未确定时保留待分配金额，不能让汇总漏项。

采用已确认显示名称，如 App 订阅、手机宽带费用；长期结束且本月计划、实际、待付均为零的条目默认隐藏，有历史或差异时可展开查看。未知金额、未设预算、未付已到期不能按零值过滤。年度表仅在整行全年均为已知零且无未结事项时隐藏，不影响计算或历史。

### 14.5 分享与导出

个人完整视图和 expense_only 分享视图具有不同数据合同。后者允许年度／月份、费用用途、预算金额、必要口径说明及来源截止；禁止收入、账户余额、净资产、留存、目标缺口、收入占比、私人账户标识、原件路径和完整报告链接。文件名、图片文本、PDF 元数据、无障碍文本、下载摘要和嵌入 JSON 同样遵守白名单。

服务端在生成 DTO 时裁字段，渲染器不得先拿完整报表再用 CSS 隐藏。修改被隐藏的私人值，expense_only 的可见内容及输出数据必须保持不变；支出本身仍属于用户主动选择分享的资料。

PDF、PNG 和 Excel 来自同一报告快照，不重新拼装另一套金额。PDF／图片嵌入或使用明确的简体中文字体；测试“径、预算、费用”等字形。PNG 支持 Safari 可用的分享／保存路径；浏览器不支持分享时提供下载。默认不创建公网分享链接。

### 14.6 批次处理与分析入口

添加账单流程按闭环规格第 3 节；failed、partial、duplicate-only、completed 的文案和后续动作分别验收，整文件失败不能显示成功勾。手机和桌面均可从批次恢复到本批交易／疑点，不要求用户记住月份或内部账户 ID。

分析页面先展示程序计算的结果，再提供“准备交给 Codex”生成解释。等待、真实运行、部分完成和失败分开；应用内一键启动只有 R11 通过后才出现。已有偏好保持墨黑默认与深绿／藏蓝选项，不为本版重新设计页面组件。

## 15. 工程架构与现有代码复用

### 15.1 运行形态与技术选择

采用一个本机 Python 服务：FastAPI 提供 HTTP API 和已构建静态前端，SQLite 保存权威业务数据。React＋TypeScript＋Vite 负责前端；不为本地单用户后台引入 SEO、SSR 或另一套 Node 生产服务。数据模型／DTO 用显式校验，前端类型由 OpenAPI 或同一 schema 生成，不能手工维护互相矛盾的两套字段。

本地 MCP 使用 stdio 薄适配器，通过受限本机内部接口调用同一 application service。应用服务是业务写入与派生计算的唯一入口；MCP 不单独打开私人 SQLite 直写。现有事务编排仍集中在 app/main.py；实施时先抽最小共用业务命令和可信调用者身份，不复制一套“AI 编辑”代码，也不把浏览器 Cookie 交给 MCP。应用未运行时 MCP 返回 service_unavailable，不暗中启动第二个业务服务或丢弃任务。应用启动方式不依赖 Codex。

原型迁移优先使用 Python 标准 SQLite 驱动、显式 SQL repository 与有序 migration 文件；不要求通用 ORM、消息中间件、向量库或多个微服务。模型上下文检索先用结构化过滤及中文商户别名，必要时再评估全文检索。

~~~mermaid
flowchart LR
    F[账单与订单文件] --> E[ETL 适配器]
    U[桌面或手机前端] --> H[HTTP API]
    C[Codex] --> M[stdio MCP 薄适配器]
    M --> A[共用应用命令与查询]
    H --> A
    E --> A
    A --> V[证据 规则 版本及金额校验]
    V --> D[(SQLite 与不可变原件)]
    D --> Q[三表 预算 预实 预测计算]
    Q --> H
    Q --> X[Excel PDF PNG 与只读快照]
~~~

UI、MCP 和 ETL 分别限定权限，但调用相同业务命令。模型运行不持有 SQLite 写事务；数据库错误不能被 AI 修复为一笔“其他收入”。

## 16. 数据与状态合同

### 16.1 数据表职责

以下是目标逻辑模型；同生命周期的小对象可用 JSON 字段合并，不要求每行一张物理表。主键采用稳定 ID，保留已有 row_* ID 的 legacy 映射；账户或供应商 ID 不能跨来源假定全局唯一。

| 对象 | 关键字段／唯一性 | 写入及计算规则 |
|---|---|---|
| source_artifacts | id、sha256、原文件名、受控路径、来源、获取时间；哈希唯一 | 文件只读归档，不因分类、重跑或重命名覆盖。 |
| import_batches／source_rows | 批次、artifact_id、parser_version、源行定位、raw_json、解析值、错误；同原件／解析版本／行唯一 | 新解析保留旧结果，来源更正作为新观察版本；预览和实际应用有独立状态。 |
| accounts／account_scopes | id、机构、账户类型、币种、现金标志、范围生效日、掩码、版本 | 支付通道与真实余额账户分开；不得以通道重复创建资产。 |
| chart_accounts／classification_rules | 固定科目；规则 ID、条件、例外、动作、来源、版本、启用状态 | 本笔人工优先；规则草稿不自动启用，不能由 AI 改范围科目。 |
| transactions／transaction_versions | id、version、业务性质、状态、消费／结算日期、金额、收入子型、用途、描述、人工覆盖字段、provenance | 头表指向当前版本；版本快照记录必要业务明细，旧版本不重复计数。 |
| transaction_parts／transaction_tags | 交易版本、部分 ID、金额、用途／科目、主预算组；标签关系唯一 | 拆分金额守恒；标签允许重叠，汇总按事实 ID 去重。 |
| evidence_links | 来源行／解析版本、目标事实或交易组成、角色、匹配方法、分配金额、active_version | 多证据支持同一事实；消费证明、收付证明、用途补充分别使用。订单补充不能再占一份现金。 |
| cash_facts | 稳定 fact_id、账户、币种、收付日、规范金额、证据、解释交易 ID（可空）、版本 | 已去重的真实现金收付；可在业务性质未知时存在。直接更正经命令留历史，原始来源不改。 |
| ledger_lines／account_movements | 交易版本、模板版本、科目、账户、借／贷、金额、cash_fact_id（可空） | 当前解释的派生结果；完整业务平衡。可重建，未解释现金不强造完整分录。 |
| business_links | 类型、源／目标事实、关联金额、证据、版本 | duplicate、refund、transfer、repayment、reimbursement 等分别校验，不共用模糊抵消标记。 |
| balance_observations／coverage | 账户、币种、时点、余额定义、来源、期间、覆盖状态 | 外部观察与账面分开；覆盖未知不能成为零，观察快照不能自动生成交易。 |
| commitments／plan_occurrences／plan_actual_links | 计划版本、事项、周期、期次、应付／预计日期、已知本息、估计状态、funding_group_id、实际分配 | 全年计划可独立存在；实际唯一履约，超额或不明确关系待核。计划不入 ledger。 |
| budget_versions／budget_lines | 年度、原版、状态、basis、假设、用途、执行口径、月额、年度额度、来源事项 | 采用版冻结；消费／计划事实只产生一种主预算占用，预留不形成真实支出。 |
| budget_funding_sources（查询投影） | 预算版本、来源政策、原工资／收入／资产动用事实、净可用金额、日期、证据、source_revision | 净到账与完整薪酬分开；本人银行互转不重复计来源，公积金路径等价；已扣项有 source_already_netted 关联。 |
| budget_usage（查询投影） | 预算版本、行、计量事实、金额、日期、basis、source_revision | 从当前事实按执行规则生成，可缓存重建；不允许 UI／AI 手工写一个余额来覆盖计算。 |
| work_items／proposals | 类型、目标 ID／版本、租约、上下文版本、建议、依据、校验／应用结果 | AI 状态与交易状态分开，重试不产生新事实。 |
| change_log／operation_results | request_id、负载摘要、操作者、前后值、原因、时间、结果；请求唯一 | 操作者由接口身份确定，不信任客户端 self-declared human；同键不同负载报冲突。 |
| investment_products／investment_events／holding_observations | 产品、账户、份额、成交、费用、成本证据、净值与时点、原始引用 | 份额及金额精确计算；快照不伪造历史成交；缺成本的收益未知。 |
| reimbursement_memos | 事项、可选垫付／退款／回款关联、已知待收及未知尾款 | 不生成报销应收资产，不要求先精确配完才累计回款 R。 |
| report_snapshots／analyses | 查询、basis、数据／规则／预算／范围版本、覆盖、结果、事实引用、生成时间 | 快照不可变；当前版本变化后旧分析及报告标过期，导出可复现。 |
| schema_migrations／app_metadata | schema_version、data_revision、规则集版本、显示政策版本 | 每个成功业务事务一次推进 data_revision；不能用文件 mtime 代替业务版本。 |

cash_facts 与 ledger_lines 不分别加总进现金表：现金表以去重 cash_facts 为事实集合，完整业务的现金分录引用同一 fact_id 并进行金额一致性校验；尚未解释的现金只出现在待解释区。非现金消费、估值、计划没有 cash_fact。修正交易金额若涉及真实收付，必须同时校验及更新相应现金事实版本；只改消费日期不移动现金日期。

### 16.2 金额与日期

MoneyDTO 统一为 currency、minor（整数的十进制字符串）、exponent；例：CNY、"12345"、2 表示 123.45 元。SQLite 用整数最小单位；每个金额的 minor 支持 −9223372036854775807 至 +9223372036854775807，必须是规范整数串，拒绝小数、指数写法及超界值。科目借贷行的金额为非负，方向另列；现金净变动和费用冲回可为负。聚合用可检查溢出的整数运算，返回值仍须在声明范围内，不能让 SQLite SUM 溢出或转浮点。前端不得 parseFloat 后累计金额。汇率、份额和净值以十进制字符串传输，后端用 Decimal 计算并显式舍入。

原始金额原样保留；规范账户净变动以资产净额增加为正、减少为负：信用消费增加欠款时为负，偿债时为正。这不等于原始银行符号，也不等于费用正负。内部借／贷列另存，不以一个 signed_amount 同时表达全部语义。

业务日期使用 YYYY-MM-DD，自然月界限采用 Asia/Shanghai；操作时间保存带时区时间戳。日期范围 API 使用 start 含、end_exclusive 不含。原币实际结算优先于估算，公共汇率不能覆盖已经确认的人民币金额。

### 16.3 相互独立的状态

| 对象 | 状态 | 转移边界 |
|---|---|---|
| 导入批次 | received → parsed／partially_parsed／failed → processed／partially_processed | 原件接收、解析成功和业务应用分别统计；重试只补失败项或产生新解析版本。 |
| 业务解释 | unresolved → confirmed；另有 excluded／merged | unresolved 可以有已知现金；confirmed 可仍缺细分类。性质未知不得用 confirmed 的未分类收入兜底。 |
| 分类 | unclassified／suggested／classified | 分类状态不改变已明确消费的金额是否计入。 |
| AI 工作项 | queued → leased → applied／needs_review／rejected；可 cancelled；过期重新 queued | 稳定问题键、任务代次、尝试计数与依赖读集按闭环规格第 4 节；首次旧令牌提交无效，已成功同请求重放返回原结果。 |
| 计划 | planned／partially_fulfilled／fulfilled／cancelled | 只有实际分配可更新履约；计划修订不改变已发生事实。 |
| 预算 | draft → adopted → superseded | 采用版保留，情景草案无业务效果。 |
| 结果完整性 | complete／partial／unavailable | complete 仅针对报告声明的范围；缺口和原因结构化返回。 |

导入批次、解析尝试及 AI 执行状态的细分以闭环规格第 3.3 节为准。财务 data_revision 与工作项／运行状态修订分开；领取任务、重试或保存分析不使账本虚假变化。疑点的 dismissed 或 snoozed 仅改变提醒展示，不隐式确认业务。当前交易、计划、分类和 AI 状态不能合成一个 posted 布尔值。

### 16.4 去重与关联的自动化边界

确定重导用文件哈希＋来源行；同来源覆盖用来源命名空间＋账户＋源交易 ID；跨来源强关联使用带类型和发行方的可靠支付／订单编号及一致金额币种。不同来源局部编号恰好相同不构成强关联。人工确认关系保留原证据和确认人。

无强 ID 时，首版仅形成候选。后续通过专门验收的适配器可扩大补证据白名单：如当前付款卡、币种、金额、同日双向唯一，以及跨日不超过已验证窗口且完整商户一致。不是所有格式都可沿用该规则。出现多候选、真实同额重复消费、不同支付渠道或退款累计字段时，创建候选而不自动合并或生成退款。

资金证据与经济事项分开；每个账户的实际变动只能由一份有效证据产生一次效果。两端独立 source_id 不代表两笔完整双边业务，不能凭对端账户字段各造一份还款；可靠关联后另一端补证据，未关联保持待核且不重复推造对端。模板校验范围包括金额守恒、已分配金额上限、币种、现金日期、来源占用角色、人工覆盖字段和状态。字段完整及 AI 高置信度不能取代业务证据。

## 17. HTTP、MCP 与 AI 合同

### 17.1 共用命令与查询

所有写请求包含 request_id、expected_version（按对象）、payload；新增操作也检查来源唯一性。批量请求返回逐项状态；同一业务组的多个变化一次事务提交。业务命令至少包括导入应用、交易修改／拆分／合并／撤销、业务关联、余额观察、规则预览／启用、计划修订、预算采用和投资记录。

响应统一携带 data_revision、operation_id、状态 applied／needs_review／conflict／rejected、影响对象与指标、warnings。查询返回 basis、currency、period、as_of、versions、coverage、unknown_amounts、drilldown；未知金额使用 null＋原因，不输出字符串“0”。

HTTP 主路径（以下均使用 /api/v1 前缀）：

| 接口族 | 方法与职责 | 写权限 |
|---|---|---|
| /imports | POST 上传／预览／应用；GET 批次、错误与来源覆盖 | 本机用户；仅受控文件内容，不接受任意本机路径读写。 |
| /transactions、/evidence | GET 列表、详情、证据和历史；POST 指定业务命令 | 用户；MCP 只可提交受限建议，不能调用任意编辑命令。 |
| /work-items、/rules | GET 疑点和规则；POST 用户处置、规则预览与启用 | 规则启用及影响历史由用户决定。 |
| /accounts、/reconciliation | GET 余额与差异；POST 观察和明确修正 | 用户；禁止差额自动配平。 |
| /budgets、/plans | GET 版本、月表、预实、排期；POST 草案、修订和采用 | 用户；采用需显示与当前版本的差异。 |
| /reports、/exports | GET 指定口径；POST 生成快照及选定导出 | expense_only 使用独立 DTO；不发公网链接。 |
| /investments | GET 持仓与收益；POST 手工／文件记录 | 只记账，不执行投资交易。 |
| /operations/{request_id}、/status | GET 稳定操作结果、版本和任务状态 | 按调用者权限返回，错误不包含完整账号或文件内容。 |
| /maintenance | POST 备份、恢复预检、迁移预检 | 本机用户专用；MCP 无此能力。 |

列表默认 50 条，最大 200 条，游标基于排序字段＋ID；相同数据修订上稳定分页。跨修订导致结果不可稳定复现时返回刷新提示。原件下载必须校验登记 ID，不允许路径穿越或替换成任意磁盘文件。

### 17.2 MCP 工具

本节列目标工具，不表示当前已接入。启动方式、状态、权限矩阵、读集、请求重放与恢复 epoch 的完整合同见闭环规格第 4—5 节。MCP 是 Codex 调用本应用；用户上传本身不启动模型。

| 工具 | 输入／输出重点 | 禁止事项 |
|---|---|---|
| list_work_items | 类型、游标、数量；目标 ID、版本及影响摘要 | 不返回完整账户身份和全部历史。 |
| claim_work_items | request_id、工作项及预期版本；令牌、到期时间 | 过期令牌不能续用或抢占人工修改。 |
| get_work_context | 工作项＋令牌；必要证据、候选、当前版本、规则及相似人工案例 | 不提供任意 SQL、任意文件读取或无限上下文。 |

| query_transactions／get_report／get_analysis_inputs | 结构化过滤、basis、期间和版本；有限明细与程序计算结果 | 不由模型自算并替代报表。 |
| propose_rule | 人工纠错事实、条件、动作、例外、来源；保存 draft | 不自动启用或重分类全部历史。 |
| submit_analysis | 报告快照、metric_id／交易引用、事实／推断／建议 | 不修改实际、规则、预算或投资账户。 |

新 AI 建议通过校验可自动应用，不要求所有交易逐笔确认；结构或证据不通过时分别 rejected／needs_review。任务建议与应用结果在同一业务提交中落库，避免任务显示完成但交易未写入。

### 17.3 AI 输入、输出和纠错优先级

上下文包含：本笔必要原始摘要、已匹配商品证据、掩码账户及支付通道、允许的业务性质和类别、有限候选关系、适用规则、人工相似案例、数据／规则版本。默认批次不超过 20 个工作项，相似案例不超过 8 笔；上下文预算可调，未选中的资料不主动发送。

建议包含 field_patches、evidence_refs、decision_basis、reason、alternatives 和 optional confidence。金额、日期、现金收付及关联变动必须引用具体事实；普通分类任务不能顺带修正金额。不存在的候选 ID 直接拒绝。

优先级：本笔人工确认 → 本笔明确商品／服务证据 → 用户已启用且适用的具体规则 → 有依据的商户默认 → 相似历史及模型推断。规则有例外时先匹配例外；证据冲突创建疑点。历史案例优先人工、较新且未被撤销的判断；平台名称不是实际商品用途。

不照抄上游 0.6 置信阈值。上线初期按业务风险验收：类别可自动应用且可回改；互转、重复、退款及债务性质必须额外通过对应关系规则。置信度只帮助排序，不能自授权。AI 缺失／超时／三次失败后任务仍可人工处理，不能按正负号生成收入费用。

“只改本笔”立即保存。“以后同类这样”先展示规则草稿、适用范围、例外和历史影响，用户保存才启用；已有人工覆盖不会被新规则静默覆盖。

### 17.4 报表解释与错误

AI 分析先读不可变 analysis input snapshot 和确定性 ReportDTO，冻结指标定义／政策／范围／覆盖／预算版本，引用 metric_id、交易 ID、版本及期间；金额事实以引用值展示。没有可验证引用的自由文本数字只能标假设，不能与报表事实混排。模型建议是待采用计划，采用需经相应用户操作和业务校验。

错误至少包含 invalid_input、unsupported_format、stale_version、lease_expired、idempotency_conflict、insufficient_evidence、ambiguous_match、allocation_exceeded、unbalanced、service_unavailable、snapshot_stale。前端给可执行的下一步；日志仅存请求 ID、状态及必要诊断，默认不记录完整流水正文。

## 18. 运行、手机访问与质量要求

### 18.1 独立运行与部署层级

核心可用层为本机服务＋浏览器：关闭 Codex 后，导入、规则、修改、对账、预算、已有报表和备份继续可用。AI 工作项等待后续手动触发，不自动唤醒会话，不预建定时任务。恢复后按稳定任务 ID 续做。第一阶段在应用准备批次、在 Codex 用户发起、回应用查看结果；应用内点击启动另按 R11 验证，不把 MCP 连通当作运行器已交付。

手机体验分两层交付：

1. 本机阶段已有响应式页面基础；手机可读 PDF／PNG 由 R08 交付；这些导出可直接在手机查看，不依赖手机连接电脑。
2. 用户确定访问方式后，单独交付受保护的 HTTPS／私有访问路径、设备认证、会话撤销和 PWA。PWA 安装不会让本机 localhost 自动变成手机可访问地址；电脑休眠时不能承诺实时访问。

一期不做完整离线编辑、冲突合并或多端写队列。可选择保存只读报告快照，显示生成时间、版本及“离线快照”；离线不能显示已同步。本设备登出时清理本应用缓存；远程撤销立即阻止后续服务访问，设备下次连接时清缓存，不能承诺远程抹掉离线设备已保存的文件。缓存默认关闭，仅用户主动选择；不缓存原始附件和完整证据。完整云同步另立范围，不改变 SQLite 单机权威文件的位置。

### 18.2 存储、权限与恢复

SQLite 在本机非同步目录启用外键、短事务和经验证的 WAL 配置；启动记录 schema 及运行库版本。仅服务进程写业务，维护操作和写事务受控；写入繁忙有有限重试和明确状态。数据库不多机同时打开同步盘副本。

默认回环监听，校验 Host／Origin；UI 有本机会话认证和跨站写保护，MCP 内部接口使用独立受限令牌。声明 actor 来自可信接口身份。手机模式另加传输保护及设备认证；不因单用户就向局域网开放无认证 API。

原件、数据库、预算配置、报告、日志与备份不入代码仓库，不声称 SQLite 自带加密。测试、演示和外部问题报告只用合成资料。传给 Codex 的选中字段会进入模型上下文，本地存储不等于模型不接收这些字段。

使用 SQLite 一致性备份接口，记录对应 data_revision、schema、规则／预算版本、原件哈希清单和导出版本。原件先写临时文件、校验后原子归档，提交时才引用；备份按数据库快照所引用的不可变文件取清单。失败的临时文件可清理，未确认孤儿原件不得随意删。

恢复先在独立目录检查哈希、SQLite 完整性、外键、版本和关键报表；验证通过后才提供切换，不覆盖正在使用的数据。每次 schema 升级前备份；应用不兼容更高 schema 时拒绝写入并说明原因。

### 18.3 可验证的质量目标

以下是交付验收目标，不是目前已测得的性能：

- 金额：所有业务算例精确到币种最小单位；拆分、年度分配、导出小计和汇总守恒。
- 性能：在记录了硬件／运行库的本机环境，以 5 万笔合成交易为基准，分页查询及常用月表热读取 p95 不超过 500ms；首次年度计算目标不超过 3 秒。超时工作显示进度，不冻结页面。耗时不包含 AI 等待。
- 导入：1 万行标准 CSV 提供进度、逐行错误和取消点；取消只停止后续业务组，不留下半笔业务。不同实际格式独立测量，不承诺同一耗时。
- 交互：390px 宽手机下主要阅读和操作不横向溢出；N×12 表允许显式横向滚动。键盘可操作，状态不只用颜色表达；费用为零／未知的展示规则一致。
- 恢复：进程在写入前后中断、请求超时重试和并发人工修改均满足原子性及幂等；任务、证据和审计可恢复。
- 导出：同一报告版本在 UI、Excel、PDF、PNG 金额一致；简体字形、零项隐藏、分享隐私用文本和视觉两种方式核查。

## 19. 实施、迁移和完成标准

### 19.1 实施顺序

v0.5 以[实施计划](../plans/implementation-plan.md)的 R00—R10 增量切片执行，T01—T09 仅保留追踪映射。先并行最低恢复、首个原生导入／口径修复、最小 MCP 分类；再扩来源、对账与确定性预实分析、AI 解释；后续补现金安排、工资债务、导出及投资。已完成迁移、凭证、维表查询和界面不重做；确定性分析不再依赖全部未来现金预测。

本机完整一期包含三表、预算／预实、文件 ETL、直接编辑／复核、Codex MCP、债务公积金、手工投资闭环和可验证恢复。T09.01 响应式体验及 T09.02 手机导出为交付要求；T09.03 受保护手机在线访问在方式确定后独立验收，不以等待该选择阻塞本机一期。

### 19.2 已完成迁移与后续兼容

既有资料已采用新应用库并保留 data/finance_processed.sqlite3 和输出作为只读迁移基线；以下迁移规则用于核对及新增明确来源，不能重新执行全量覆盖。历史对象与新交易先统一有效事实／证据／可关联金额读取合同，跨模型退款与关系复用同一校验，保留存储适配器。不在现有生产资料上直接试验 schema。旧脚本仍可在隔离目录重跑对照，不允许同时向新应用库写入。

迁移输入包括现有来源清单、原始文件及哈希、加工交易、人工确认／覆盖、关系、已有分类证据、当前预算 payload／results、展示政策、还款计划和投资已知快照。缺失审计历史不能根据当前值伪造：保存“迁移时已知当前值”和可取得来源。

旧 row_* ID 建 legacy_id_map，保留用户曾确认的交易引用；同一项跨 Excel、JSON 和 SQLite 出现时先确定权威来源及版本，不能各迁入一次。人工确认优先于旧机器推定，已采用预算的每项参数保留来源。默认迁移当前选定预算，早期旅行／大件等已被替代方案作为历史，不复活为额外扣款。

步骤为：一致性备份 → 合成全链路验收 → 已授权少量真实样本适配 → 一段资料较齐期间对照 → 扩展至已有 2026 资料 → 预算 12 个月逐格对照 → 用户核对差异 → 切换日常入口。每批具有稳定 migration_id，可去重重跑及回退到切换前版本。已有资料授权不需重复询问；新增账户或外部上传另按实际范围处理。

对照同时检查收入、费用、现金、负债、业务数量、未解释金额、预算各月和汇总，而不只核对一个年度总数。已知口径修正产生的差异独立列证据与理由，不能偷偷调整本金或报销凑平。

### 19.3 版本迁移政策

v0.3 报销模式继续生效：旧版已从费用剔除的工作垫付及真实退款恢复为实际费用及冲减；报销回款计 4005／报销回款，移除同笔报销应收资产效果，只保留备忘。逐笔检查是否已经恢复，防止重复。家庭赞助独立分型，不抵费用。

v0.4 不因为参考仓库而改变科目数、消费日、还款日、报销收入或已采用预算。变化是应用结构、展示和执行合同；如新应用发现原型不满足某条合同，按差异处理，不把原型的实现状态等同目标已完成。

### 19.4 验收层级

1. 业务正确：AC-01—AC-35 的财务及恢复场景按所交付分支逐项验收；现有测试数不等于这些场景已全部通过。
2. 应用可用：新增 AC-36—AC-57 中本地页面、接口、预算执行、来源、分享及迁移分支通过。AC-47 的远程设备认证、PWA／只读缓存等分支仅在 T09.03 启用对应能力后适用，不作为本地一期阻断；不得以不适用冒充已通过。
3. 新闭环：AC-58—AC-78 覆盖来源身份、任务恢复、AI 自动权限、分析、修复反例和阶段门槛；正确率、覆盖率、待核与拒绝分别统计。
4. 真实接入：每个真实来源格式、真实 Codex MCP、手机方式分别记录 tested／untested；模拟接口通过不写成真实平台接通。
5. 真实迁移：只对明确的来源／账户／期间宣布完成，保留期初、投资成本、未取得账单等缺口。

## 20. 待确定事项与默认处理

| 事项 | 本版默认及不阻塞的工作 | 实际限制 |
|---|---|---|
| 应用内一键启动 Codex | 首期采用用户在 Codex 发起；后续 R11 合成验证技术与隔离，用户决定启用 | 不默认后台执行、增加模型 API 或创建定时任务。 |
| 手机从外部网络访问的方式、是否常开设备 | 先完成本机、响应式界面及手机导出；预留只读快照接口 | 不默认云部署，不承诺电脑休眠后在线。 |
| 尚未取得的导出格式与完整月份 | 复用已有样本和合成 fixture，逐来源标覆盖 | 不把缺失月份当零或声称全部账户完整。 |
| 贷款起点、真实本息、投资成本 | 先录已知现金／计划／快照 | 绝对余额、收益和精确逐日预测可能不可用。 |
| 主观行为标签 | 默认 unknown，可由用户定义 | 不凭金额自动判断冲动或不合理，不影响消费入总额。 |
| 外部基金平台读取与公开净值接口 | 手工／文件闭环先交付 | 需另验授权、覆盖、费用和时效，不假设能读天天基金本人持仓。 |
| 备份地点、保留数量、设备加密偏好 | 本机一致性备份与独立恢复先做 | 不擅自上传私人备份，不声称已经加密。 |

以上均不是重新讨论已经确认的工资、订阅、宠物、交通或储蓄目标。私人参数从最新已采用预算迁移，变更需保留修订；文档不复制一套可能过期的私人金额。
